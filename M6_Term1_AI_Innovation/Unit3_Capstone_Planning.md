# หน่วยที่ 3: Capstone Project Planning (คาบที่ 14–19)

---

### คาบที่ 14: ตั้งทีม กำหนดบทบาท และเลือกหัวข้อ Capstone
- **จุดประสงค์การเรียนรู้:**
  1. จัดตั้งทีม Capstone (2–4 คน) และกำหนดบทบาทหน้าที่หลักของสมาชิกแต่ละคน (เช่น Project Lead, AI/Data, Hardware/IoT, UI/UX & Docs) ได้
  2. ตกลงหัวข้อโครงงาน Capstone และกติกาการทำงานร่วมกันของทีม (Team Charter) ได้
- **แนวคิดหลัก:** โครงงานระยะยาว 2 ภาคเรียนจะสำเร็จได้เมื่อสมาชิกทุกคนมีบทบาทชัดเจน มีกติกาการสื่อสารร่วมกัน และรับผิดชอบงานส่วนของตนเอง
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ชี้แจงโครงสร้าง Capstone ต่อเนื่อง 2 ภาคเรียน (ม.6/1 ต้นแบบ, ม.6/2 สมบูรณ์+Pitch) |
  | 5–15 นาที | บรรยาย/สาธิต | แนะนำ 4 บทบาทหลักในทีมพัฒนา AI/Robotics และวิธีเขียน Team Charter |
  | **15–50 นาที (70%)** | **โครงงานปลายคาบ** | ลงมือทำเอง (จัดทีม + กำหนดบทบาท + ยืนยันหัวข้อ) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ใบจัดตั้งทีมและข้อตกลงการทำงาน (Team Charter)
  - **โจทย์/สถานการณ์:** จัดตั้งทีมพัฒนา Capstone อย่างเป็นทางการ พร้อมตกลงหัวข้อโครงงานและบทบาทรับผิดชอบของแต่ละคน
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ใบจัดทีม 1 หน้า ระบุ: ชื่อทีมและหัวข้อโครงงาน, รายชื่อสมาชิกพร้อมบทบาทหลัก/บทบาทรอง, ช่องทางสื่อสาร, และข้อตกลงทีม (เช่น ส่งงานตรงเวลา, แก้ความขัดแย้งอย่างไร)
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. รวมทีม 2–4 คนที่มีความสนใจและทักษะเสริมกัน (เช่น มีคนถนัดโค้ด/AI + คนถนัดฮาร์ดแวร์ + คนถนัดออกแบบ/สื่อสาร)
    2. ตกลงเลือกหัวข้อ Capstone 1 เรื่อง (ต่อยอดจากหน่วยที่ 2)
    3. กำหนดบทบาทหลักและบทบาทรองของทุกคน
    4. ลงนามข้อตกลงทีมและส่งครูบันทึกทะเบียนทีม
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - สมาชิกครบ 2–4 คนและแบ่งบทบาทชัดเจนสมดุล (4 คะแนน)
    - หัวข้อโครงงานชัดเจน มีความเป็นไปได้ (3 คะแนน)
    - มีข้อตกลงทีมที่ปฏิบัติได้จริง (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ทีม 3 คน แบ่งเป็น Lead+IoT (นาย ก), AI/Data (น.ส. ข), UI/Docs (นาย ค) พร้อมหัวข้อและข้อตกลงชัดเจน
  - **ตัวเลือกเสริม (Extension):** ตั้งชื่อผลิตภัณฑ์/โปรเจกต์ให้จำง่ายและออกแบบโลโก้ชั่วคราว
  - **แนวทางช่วยเหลือ (Scaffold):** แจกแบบฟอร์ม Team Charter 1 หน้าและคำอธิบายหน้าที่ของ 4 บทบาท
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, LibreOffice Writer / Markdown [เสริม], แบบฟอร์มใบจัดทีม
- **คำถามสะท้อนคิดปิดคาบ:**
  1. หากสมาชิกในทีมคนใดคนหนึ่งป่วยหรือไม่สามารถทำงานช่วงสอบได้ บทบาทรองที่กำหนดไว้จะช่วยทีมได้อย่างไร?

### คาบที่ 15: เขียน Problem Statement, เป้าหมาย, ขอบเขต และเกณฑ์วัดความสำเร็จ
- **จุดประสงค์การเรียนรู้:**
  1. เขียน Problem Statement เป้าหมาย และขอบเขตของโครงงาน (In-Scope / Out-of-Scope) ได้อย่างชัดเจน
  2. กำหนดเกณฑ์วัดความสำเร็จ (Success Metrics) ที่วัดผลได้ทั้งเชิงเทคนิคและเชิงผู้ใช้ได้
- **แนวคิดหลัก:** การกำหนดขอบเขตว่า **"จะทำอะไร" (In-Scope)** และ **"จะยังไม่ทำอะไร" (Out-of-Scope)** คือกุญแจป้องกันไม่ให้โครงงานบานปลายจนทำไม่เสร็จ
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ทบทวนผลทดสอบต้นแบบกระดาษจากคาบ 13 |
  | 5–15 นาที | บรรยาย/สาธิต | สอนเขียน Problem Statement, In/Out of Scope, และ Success Metrics (KPI) |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | ตัวอย่างการตัดขอบเขตให้พอดี (เช่น ทำแยกขยะ 3 ประเภทก่อน ไม่ทำ 20 ประเภท) |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ร่างโครงงาน Capstone (Project Charter v1)
  - **โจทย์/สถานการณ์:** เขียนเอกสารกำหนดทิศทางและขอบเขตของโครงงาน Capstone ให้ชัดเจนก่อนออกแบบสถาปัตยกรรมระบบ
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** เอกสารร่างโครงงาน 1 หน้า ประกอบด้วย: Problem Statement, วัตถุประสงค์ 2–3 ข้อ, ขอบเขต (In-Scope & Out-of-Scope), และเกณฑ์วัดความสำเร็จ ≥ 3 ข้อ (มีตัวเลขวัดได้)
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เขียน Problem Statement (ใคร เจอปัญหาอะไร ส่งผลอย่างไร)
    2. กำหนดวัตถุประสงค์และขอบเขต In-Scope (ต้องทำให้เสร็จ) vs Out-of-Scope (ยังไม่ทำในเวอร์ชันนี้)
    3. ตั้งเกณฑ์ความสำเร็จเชิงตัวเลข (เช่น โมเดลแม่นยำ ≥ 85%, ตอบสนองภายใน ≤ 2 วินาที, ผู้ใช้ทดสอบ ≥ 3 คนให้คะแนน ≥ 4/5)
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - Problem Statement ชัดเจนเชื่อมโยงกับผู้ใช้จริง (3 คะแนน)
    - ขอบเขต In-Scope / Out-of-Scope สมจริงและป้องกันงานบานปลาย (4 คะแนน)
    - เกณฑ์วัดความสำเร็จเป็นรูปธรรมและวัดผลได้จริง (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ระบุ Out-of-Scope ชัดเจน เช่น *"ยังไม่รองรับการจ่ายเงินออนไลน์และยังไม่ทำแอป iOS/Android แท้ (ใช้เว็บแอปแทน)"*
  - **ตัวเลือกเสริม (Extension):** แบ่งเป้าหมายเป็น MVP (Minimum Viable Product) สำหรับ ม.6/1 และ Full Feature สำหรับ ม.6/2
  - **แนวทางช่วยเหลือ (Scaffold):** แจกเทมเพลต Project Charter 4 ช่องพร้อมตัวอย่างเกณฑ์วัดความสำเร็จ
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, LibreOffice Writer / Markdown [เสริม]
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ทำไมการเขียน Out-of-Scope (สิ่งที่จะไม่ทำ) จึงสำคัญไม่แพ้สิ่งที่จะทำ?

### คาบที่ 16: ออกแบบสถาปัตยกรรมระบบ/โมเดล และเลือกข้อมูล/อุปกรณ์
- **จุดประสงค์การเรียนรู้:**
  1. ออกแบบผังสถาปัตยกรรมระบบ (System Architecture) เชื่อมโยง Input – AI/Logic – Backend – UI/Hardware ได้
  2. เลือกชุดข้อมูล (Dataset/Data Source), โมเดล AI, และรายการอุปกรณ์ฮาร์ดแวร์/ซอฟต์แวร์ (Tech Stack) ที่เหมาะสมกับงบประมาณและเวลาได้
- **แนวคิดหลัก:** สถาปัตยกรรมระบบที่ดีต้องเลือกเครื่องมือที่ทีมเคยฝึกมาแล้วใน ม.4–ม.5 (Python, JupyterHub/PyTorch/YOLO, ESP32-S3, MQTT, Gradio/Node-RED) มาประกอบกันอย่างลงตัว
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ทบทวนเครื่องมือทั้งหมดที่เรียนมาตลอด ม.4–ม.5 |
  | 5–15 นาที | บรรยาย/สาธิต | แสดงตัวอย่าง System Architecture 2 สาย (สาย Software/Vision AI และสาย AIoT/Robotics) |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | ร่างกล่อง Input → Process/AI → Output ของทีม |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** พิมพ์เขียวสถาปัตยกรรมระบบ Capstone (System Architecture & Tech Stack)
  - **โจทย์/สถานการณ์:** ออกแบบผังเทคนิคทั้งหมดของโครงงาน เพื่อใช้เป็นแบบแปลนตลอด 18 คาบของการพัฒนา
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** แผนภาพสถาปัตยกรรมระบบ 1 หน้า + ตาราง Tech Stack & Data/Hardware Spec (ระบุ Input, โมเดล/อัลกอริทึม, แหล่งข้อมูล, โปรโตคอลเชื่อมต่อ, UI/Hardware Output, และรายการอุปกรณ์ที่ต้องเตรียม)
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. วาดผังเชื่อมโยงทุกองค์ประกอบ (เช่น กล้อง/เซนเซอร์ → Python/ESP32-S3 → โมเดล MobileNet/YOLO/sklearn → แดชบอร์ด/เว็บแอป/รีเลย์)
    2. ระบุรายละเอียดข้อมูล: ต้องเก็บเองกี่ภาพ/กี่แถว หรือใช้ Dataset ไหน
    3. ระบุรายการอุปกรณ์ฮาร์ดแวร์ที่ต้องเบิกหรือจัดหา (ถ้ามี)
    4. ตรวจทานความเข้ากันได้ของแต่ละส่วน (เช่น ESP32-S3 ส่งไปหา Python ทางไหน?)
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ผังระบบครบถ้วน เชื่อมต่อกันได้จริงทางเทคนิค (5 คะแนน)
    - เลือกโมเดล ข้อมูล และอุปกรณ์เหมาะสมกับทักษะและเวลา (3 คะแนน)
    - เอกสารชัดเจนพร้อมนำไปวางแผน Sprint (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ผังแสดงชัดเจนตั้งแต่ผู้ใช้ถ่ายภาพบนเว็บ Gradio → FastAPI/Python → YOLO + MobileNet → คืนคำตอบ + บันทึกสถิติลง CSV/Sheets
  - **ตัวเลือกเสริม (Extension):** ระบุแผนสำรองทางเทคนิค (Fallback) หากอุปกรณ์หลักหรือโมเดลหลักช้าเกินไป
  - **แนวทางช่วยเหลือ (Scaffold):** แจกไอคอนและตัวอย่างผังสถาปัตยกรรม 3 รูปแบบ (Web AI, AIoT, Robotics)
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, Draw.io / โปรแกรมออกแบบออฟไลน์ (LibreOffice Impress / Draw.io) [เสริม] / LibreOffice Impress / Markdown Slides [เสริม]
- **คำถามสะท้อนคิดปิดคาบ:**
  1. จุดเชื่อมต่อ (Interface) ไหนในผังระบบของคุณที่คิดว่าจะยากที่สุดตอนพัฒนาจริง?

### คาบที่ 17: แผนงาน (Kanban/Gantt), ความเสี่ยง และงบประมาณ
- **จุดประสงค์การเรียนรู้:**
  1. แตกงานใหญ่จากสถาปัตยกรรมระบบออกเป็นงานย่อย (Task Breakdown) และวางแผนบนบอร์ด Kanban (To Do / Doing / Done) หรือ Gantt Chart สำหรับ Sprint 1–3 ได้
  2. ประเมินความเสี่ยงทางเทคนิค/เวลา และสรุปงบประมาณที่ต้องใช้จริงได้
- **แนวคิดหลัก:** การแตกงานใหญ่เป็นชิ้นเล็ก ๆ (Task ละ 1–2 คาบ) บนบอร์ด Kanban ช่วยให้ทีมเห็นความคืบหน้าและรู้ทันทีเมื่อมีงานติดขัด
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | แนะนำโครงสร้าง Sprint 1–3 ในหน่วยที่ 4 (คาบ 20–37) |
  | 5–15 นาที | บรรยาย/สาธิต | สาธิตการสร้าง Kanban Board (Trello/Local Git Server (Projects/Issues)) และตาราง Risk Matrix |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | ลองแตกงานส่วนแรกออกเป็น 4 การ์ดพร้อมระบุผู้รับผิดชอบ |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** บอร์ดแผนงาน Kanban และแผนรับมือความเสี่ยง
  - **โจทย์/สถานการณ์:** วางแผนการทำงานของทีมสำหรับ 18 คาบพัฒนา (Sprint 1: แกนระบบ, Sprint 2: โมเดล/ฮาร์ดแวร์+เชื่อมต่อ, Sprint 3: รวมระบบ+UI+ทดสอบ)
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** (1) ลิงก์บอร์ดงาน Kanban (Trello/Local Git Server (Projects/Issues)) ที่มีรายการงานย่อย ≥ 12 การ์ด แบ่งตาม Sprint พร้อมผู้รับผิดชอบ, (2) ตารางความเสี่ยง (≥ 3 ข้อ + แผนสำรอง) และตารางงบประมาณฉบับสมบูรณ์
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. สร้างบอร์ด Kanban ที่มีคอลัมน์ `Backlog (Sprint 1/2/3)`, `To Do`, `Doing`, `Done`
    2. แตกงานจากผังระบบคาบ 16 เป็นการ์ดงานย่อย ๆ ใส่ป้าย Sprint และชื่อคนรับผิดชอบ
    3. เขียนตารางความเสี่ยง 3 ข้อ (เช่น อุปกรณ์เสีย, ข้อมูลน้อย, โมเดลไม่แม่น) พร้อมแผนรับมือ
    4. สรุปงบประมาณต้นแบบจากคาบ 6 ฉบับอัปเดตตามอุปกรณ์จริง
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - แตกงานย่อยครบ ≥ 12 การ์ด ครอบคลุม Sprint 1–3 และมีผู้รับผิดชอบชัดเจน (5 คะแนน)
    - ตารางความเสี่ยงระบุวิธีรับมือที่ทำได้จริง (3 คะแนน)
    - งบประมาณสอดคล้องกับรายการอุปกรณ์ในสถาปัตยกรรม (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** บอร์ด Trello มีการ์ดงาน 15 ใบเรียงตาม Sprint 1–3 ชัดเจน และตารางความเสี่ยงระบุว่า "ถ้าเซนเซอร์สั่งไม่ทัน → ใช้ชุดสำรองห้องแล็บหรือจำลองค่าแทนระหว่างรอ"
  - **ตัวเลือกเสริม (Extension):** ทำ Timeline Gantt Chart ประกอบเพื่อเห็นช่วงเวลาที่งานต้องรอต่อกัน (Dependencies)
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมตัวอย่างรายการ Task มาตรฐานสำหรับ Sprint 1, 2, 3 ให้ปรับใช้
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, Trello / Local Git Server (Projects/Issues) / LibreOffice Calc / CSV บน NAS [เสริม]

### คาบที่ 18: พิสูจน์ความเป็นไปได้ขั้นต่ำ (Proof-of-Concept: PoC)
- **จุดประสงค์การเรียนรู้:**
  1. ระบุส่วนประกอบที่มีความเสี่ยงทางเทคนิคสูงสุดของโครงงาน Capstone ได้
  2. สร้างชิ้นงาน Proof-of-Concept (PoC) ขนาดเล็กที่ทำงานได้จริงเพื่อยืนยันว่าแนวคิดหลักทำได้ทางเทคนิค
- **แนวคิดหลัก:** PoC (Proof-of-Concept) ไม่ใช่ระบบเต็ม แต่เป็นการทดสอบ "จุดที่เสี่ยงที่สุด" ด้วยวิธีที่เร็วที่สุด (เช่น ลองรันโมเดลกับภาพ 5 ภาพ, ลองต่อเซนเซอร์ 1 ตัวส่งเข้า Python) เพื่อลดความเสี่ยงก่อนเริ่ม Sprint 1
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | อธิบายความต่างระหว่าง PoC (พิสูจน์ว่าทำได้ไหม) กับ Prototype (ต้นแบบใช้งาน) |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ** | ลงมือทำเอง (สร้าง PoC ชิ้นเล็กที่รันได้จริง!) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ชิ้นงาน PoC พิสูจน์แกนเทคนิค (Mini Proof-of-Concept)
  - **โจทย์/สถานการณ์:** ทีมต้องพิสูจน์ให้คณะกรรมการเห็นในคาบ 19 ว่าเทคโนโลยีหลักของโครงงานทำงานได้จริง ไม่ใช่แค่ไอเดียบนกระดาษ
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** PoC ที่ทำงานได้จริง 1 ชิ้น (เช่น โค้ดทดสอบโมเดลกับข้อมูลตัวอย่าง 5–10 ชิ้น, หรือวงจรเซนเซอร์ 1 ตัวที่อ่านค่าเข้าคอมพิวเตอร์ได้, หรือ Script API เชื่อมต่อเบื้องต้น) พร้อมหลักฐานภาพ/วิดีโอสั้น
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เลือกจุดเสี่ยงทางเทคนิคอันดับ 1 ของทีม
    2. ลงมือสร้าง/ทดลองในขอบเขตเล็กที่สุดเท่าที่จะพิสูจน์ได้ (ใน 40 นาที)
    3. บันทึกผลลัพธ์ (รันผ่านไหม? ช้าหรือเร็ว? แม่นแค่ไหน?) เพื่อนำไปโชว์ประกอบ Proposal ในคาบ 19
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - เลือกจุดเสี่ยงหลักมาทดสอบ PoC ได้ตรงจุด (3 คะแนน)
    - PoC ทำงานได้จริงหรือได้ผลพิสูจน์ที่ชัดเจน (5 คะแนน)
    - สรุปข้อค้นพบจาก PoC เพื่อปรับแผนได้ (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ทีมทำระบบตรวจนับเม็ดยา/ชิ้นส่วนด้วย YOLO → รัน PoC ทดสอบกับภาพถ่าย 3 ภาพแล้วนับได้ 80% พร้อมเห็นชัดว่าต้องถ่ายจากมุมตรงเท่านั้น
  - **ตัวเลือกเสริม (Extension):** ทดลอง PoC จุดเสี่ยงที่ 2 (เช่น การเชื่อมต่อระหว่างบอร์ดกับเว็บ)
  - **แนวทางช่วยเหลือ (Scaffold):** ครู/TA ช่วยแนะนำขอบเขต PoC ที่จบได้ใน 40 นาทีสำหรับทุกทีม
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, JupyterHub / ชุดอุปกรณ์ฮาร์ดแวร์ตามโจทย์ทีม
- **คำถามสะท้อนคิดปิดคาบ:**
  1. หลังจากทำ PoC วันนี้ มีอะไรที่ง่ายกว่าที่คิด หรือยากกว่าที่คิดบ้าง?

### คาบที่ 19: นำเสนอ Proposal ต่อครู/คณะกรรมการ และรับข้อเสนอแนะ
- **จุดประสงค์การเรียนรู้:**
  1. นำเสนอ Project Proposal (ปัญหา, คุณค่า, สถาปัตยกรรม, แผนงาน, งบประมาณ และผล PoC) อย่างกระชับและน่าเชื่อถือได้
  2. รับฟังและบันทึกข้อเสนอแนะจากครู/คณะกรรมการเพื่อนำไปปรับขอบเขตก่อนเริ่ม Sprint 0 ได้
- **แนวคิดหลัก:** Proposal Review คือด่านตรวจคุณภาพก่อนลงทุนลงแรงพัฒนาจริง 18 คาบ เพื่อให้มั่นใจว่าโจทย์มีคุณค่าและขอบเขตพอดีเวลา
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/เตรียมระบบ | แจ้งลำดับนำเสนอ (ทีมละ 3–4 นาที + ถาม-ตอบ 2 นาที) |
  | **5–45 นาที (80%)** | **โครงงานปลายคาบ (Proposal Pitch)** | นำเสนอ Proposal + โชว์หลักฐาน PoC ต่อครู/คณะกรรมการ |
  | 45–50 นาที | สรุปผลอนุมัติ | สรุปสถานะอนุมัติและสิ่งที่ต้องปรับก่อนเริ่ม Sprint 0 |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** Capstone Project Proposal & Review
  - **โจทย์/สถานการณ์:** นำเสนอแผนโครงการต่อคณะกรรมการเพื่อขออนุมัติเริ่มพัฒนาในหน่วยที่ 4
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** (1) สไลด์ Proposal 5–7 หน้า, (2) หลักฐาน PoC จากคาบ 18, (3) เอกสารบันทึกข้อเสนอแนะและการปรับปรุง (Revision Log)
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. นำเสนอครบ 5 ประเด็น: ปัญหา/Insight → แนวทางแก้/สถาปัตยกรรม → ผล PoC → แผน Sprint & งบ → ความเสี่ยง
    2. ตอบคำถามคณะกรรมการและจดบันทึกข้อเสนอแนะทุกข้อ
    3. อัปเดตแผน/ขอบเขตตามคำแนะนำก่อนเปิด Sprint 0 ในคาบ 20
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - สไลด์ครบถ้วน เชื่อมโยงตั้งแต่ผู้ใช้จนถึงเทคนิค (4 คะแนน)
    - มีหลักฐาน PoC ยืนยันความเป็นไปได้จริง (3 คะแนน)
    - นำเสนอชัดเจน ตอบคำถามและรับฟีดแบ็กอย่างมืออาชีพ (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** นำเสนอจบใน 4 นาที โชว์คลิป PoC จากคาบ 18 และได้รับอนุมัติให้เริ่ม Sprint 0 พร้อมปรับลดจำนวนคลาสตามคำแนะนำครู
  - **ตัวเลือกเสริม (Extension):** ให้ทีมอื่นร่วมเขียนคำแนะนำเพิ่มเติม 1 ข้อต่อทีม (Peer Input)
  - **แนวทางช่วยเหลือ (Scaffold):** แจกโครงสไลด์ Proposal 6 หน้ามาตรฐาน
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** โปรเจกเตอร์, นาฬิกาจับเวลา, สไลด์ Proposal, แบบบันทึกอนุมัติโครงงาน
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ข้อเสนอแนะข้อไหนจากคณะกรรมการที่ช่วยให้โครงงานของทีมคมชัดและเป็นไปได้จริงมากขึ้น?
