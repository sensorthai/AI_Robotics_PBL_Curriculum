### คาบที่ 20: Sprint 0 — ตั้ง Repository (GitHub), บอร์ดงาน และเป้าหมาย Sprint
- **จุดประสงค์การเรียนรู้:**
  1. สร้าง GitHub Repository โครงสร้างโฟลเดอร์มาตรฐาน ไฟล์ `README.md` และ `.gitignore` เพื่อบริหารโค้ดร่วมกันในทีมได้
  2. อัปเดตบอร์ดงานและกำหนดเป้าหมายของ Sprint 1 (Sprint 1 Goal) อย่างชัดเจนได้
- **แนวคิดหลัก:** Sprint 0 คือการวางโครงสร้างพื้นฐานวิศวกรรมซอฟต์แวร์ (GitHub + README + .gitignore + Kanban) เพื่อให้ทุกคนในทีมทำงานร่วมกันได้โดยโค้ดไม่ทับกันและรหัสผ่านไม่หลุด
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | อธิบายหลักการ Agile Sprint (คาบ 20–37) และบทบาทของ GitHub |
  | 5–15 นาที | บรรยาย/สาธิต | สาธิตสร้าง Repo, เชิญ Collaborators, ตั้ง `.gitignore` (กันไฟล์ใหญ่/รหัสลับ), และ Commit แรก |
  | **15–50 นาที (70%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** บ้านของโปรเจกต์บน GitHub (Sprint 0 Setup)
  - **โจทย์/สถานการณ์:** เตรียมพื้นที่ทำงานกลางของทีมให้พร้อมสำหรับ Sprint 1 โดยทุกคนในทีมต้องเข้าถึงและอัปเดตงานได้
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ลิงก์ GitHub Repository ที่มีสมาชิกครบ, โครงสร้างโฟลเดอร์ (`src/`, `data/`, `docs/`), `README.md` ฉบับตั้งต้น, `.gitignore` และบอร์ดงานที่ย้าย Task ของ Sprint 1 มาไว้ในช่อง `To Do`
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. สร้าง Repository บน GitHub และเพิ่มสมาชิกทุกคนเป็น Collaborators
    2. สร้างไฟล์ `README.md` ใส่ชื่อโครงงาน, สมาชิก, และวิธีใช้งานเบื้องต้น
    3. สร้าง `.gitignore` (ไม่เก็บไฟล์ความลับ `secrets.py`/`.env` และไฟล์ Dataset ขนาดใหญ่เกิน 100MB)
    4. อัปเดตบอร์ดงาน Kanban ตั้งเป้า Sprint 1 (คาบ 21–24) ให้ชัดเจน
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - Repo มีสมาชิกครบ โครงสร้างโฟลเดอร์เป็นระเบียบ (4 คะแนน)
    - มี `README.md` และ `.gitignore` ถูกต้อง (3 คะแนน)
    - บอร์ดงานมีเป้าหมาย Sprint 1 และงานย่อยชัดเจน (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** Repo `github.com/team/smart-bin` มีโฟลเดอร์ `firmware/`, `ai/`, `docs/` พร้อม `README.md` และบอร์ดงาน Sprint 1
  - **ตัวเลือกเสริม (Extension):** ตั้งค่า Branch Protection หรือฝึกสร้าง Branch แยกตามหน้าที่ (เช่น `dev-ai`, `dev-iot`)
  - **แนวทางช่วยเหลือ (Scaffold):** แจกไฟล์ `.gitignore` มาตรฐานสำหรับ Python + IoT และโครง `README.md`
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, บัญชี GitHub, บอร์ดงาน (Trello/GitHub Projects)
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ทำไมเราถึงไม่ควรอัปโหลดไฟล์ข้อมูลขนาดใหญ่หลายร้อย MB หรือไฟล์ `secrets.py` ขึ้น GitHub?

### คาบที่ 21: Sprint 1 (1/4) — เตรียมข้อมูลและโครงสร้างส่วนแกนระบบ
- **จุดประสงค์การเรียนรู้:**
  1. เริ่มเก็บ/รวบรวมชุดข้อมูลจริงหรือจัดเตรียมอุปกรณ์ฮาร์ดแวร์ฐานตามสถาปัตยกรรมระบบได้
  2. เขียนโครงสร้างไฟล์เริ่มต้นและบันทึกความคืบหน้า (Commit/อัปเดตบอร์ด) ได้
- **แนวคิดหลัก:** Sprint 1 (4 คาบ) มีเป้าหมายเดียวคือ **"สร้างส่วนแกนของระบบ (Core Pipeline & Data) ให้ทำงานได้จริง"**
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up (5 นาที) | แต่ละทีมเช็กบอร์ด: วันนี้ใครทำ Task ไหนใน Sprint 1 |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (Sprint 1 Day 1)** | ลงมือพัฒนาตามบอร์ดงาน (ครูเดินให้คำปรึกษา) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** Sprint 1 Day 1 — ชุดข้อมูลตั้งต้น/โครงร่างฮาร์ดแวร์ฐาน
  - **โจทย์/สถานการณ์:** ลงมือทำงานวันแรกของ Sprint 1 เพื่อจัดเตรียมวัตถุดิบหลักของระบบ (ข้อมูล Dataset หรือ วงจรฐาน)
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** หลักฐานความคืบหน้า: ชุดข้อมูลรอบแรกที่รวบรวม/ทำความสะอาดแล้ว หรือ โครงร่างโค้ด/วงจรฐานที่ต่อเสร็จ + Commit บน GitHub / อัปเดตการ์ดบนบอร์ด
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. ย้ายการ์ดงานวันแรกไปช่อง `Doing`
    2. สายข้อมูล/AI: เก็บและจัดระเบียบ Dataset จริงของโครงงาน; สายฮาร์ดแวร์: ต่อวงจรเซนเซอร์/ตัวขับพื้นฐาน
    3. ทดสอบความถูกต้องของข้อมูล/สายไฟเบื้องต้น
    4. Commit โค้ด/เอกสารขึ้น GitHub และย้ายการ์ดที่เสร็จไป `Done`
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ลงมือทำงานตรงตาม Task บนบอร์ดงาน (4 คะแนน)
    - ได้ผลลัพธ์ชิ้นงานตั้งต้น (ข้อมูล/วงจร/โครงโค้ด) ที่ตรวจสอบได้ (4 คะแนน)
    - อัปเดตบอร์ดและ GitHub ท้ายคาบ (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** สาย AI รวบรวมข้อมูลครบ 50% และเขียนสคริปต์โหลดข้อมูลผ่าน; สาย Hardware ต่อวงจรอ่านเซนเซอร์ผ่าน
  - **ตัวเลือกเสริม (Extension):** เขียนสคริปต์ตรวจสอบคุณภาพข้อมูลอัตโนมัติ (Data Validation Script)
  - **แนวทางช่วยเหลือ (Scaffold):** ครูช่วยแบ่งงานคนที่ติดขัดให้เล็กลงเหลือระดับทำเสร็จใน 1 คาบ
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, GitHub, บอร์ดงาน, อุปกรณ์/เครื่องมือเฉพาะทีม
- **คำถามสะท้อนคิดปิดคาบ:**
  1. วันนี้มีงานไหนที่ติดขัด (Blocker) และต้องให้เพื่อนในทีมหรือครูช่วยในคาบหน้า?

### คาบที่ 22: Sprint 1 (2/4) — พัฒนาโมดูลรับข้อมูลและประมวลผลเบื้องต้น
- **จุดประสงค์การเรียนรู้:**
  1. เขียนโค้ดส่วนรับข้อมูล (Input / Data Loader / Sensor Reader) ให้ทำงานได้จริงโดยไม่มี Error ได้
  2. ทดสอบรับข้อมูลจริงเข้าสู่โปรแกรมและจัดเก็บในรูปแบบที่พร้อมส่งต่อให้โมเดล/ตรรกะได้
- **แนวคิดหลัก:** ส่วนรับข้อมูล (Ingestion Layer) ต้องสะอาดและเสถียร เพราะเป็นต้นน้ำของทั้งระบบ
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up | ตรวจบอร์ดงานและแก้ปัญหา Blocker จากคาบ 21 |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (Sprint 1 Day 2)** | ลงมือพัฒนาโมดูลรับข้อมูล/เตรียมข้อมูล |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** Sprint 1 Day 2 — โมดูลรับและเตรียมข้อมูลทำงานได้จริง
  - **โจทย์/สถานการณ์:** สร้างโมดูล Input ของระบบ Capstone ให้รับข้อมูลจริง (ภาพ/CSV/เซนเซอร์/ข้อความ) และแปลงให้อยู่ในรูปแบบพร้อมประมวลผล
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** โค้ดโมดูลรับข้อมูล (เช่น `data_loader.py` หรือ `sensor_node.py`) ที่รันผ่านและแสดงข้อมูลจริงที่รับเข้ามาได้ + Commit บน GitHub
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เขียนฟังก์ชันรับและแปลงข้อมูล (Preprocessing / Calibration)
    2. ทดสอบรันกับข้อมูลจริง ≥ 3 ตัวอย่าง
    3. บันทึกโค้ดขึ้น GitHub และอัปเดตบอร์ดงาน
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - โมดูลรับข้อมูลรันผ่านจริงกับข้อมูลทดสอบ (5 คะแนน)
    - โค้ดเป็นระเบียบ (แยกเป็นฟังก์ชัน) และอัปขึ้น GitHub (3 คะแนน)
    - การทำงานร่วมกันในทีมและอัปเดตบอร์ด (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** `preprocess.py` โหลดภาพ/CSV ของทีมและปรับขนาด/ทำความสะอาดพร้อมเข้าโมเดล หรือ ESP32 อ่านเซนเซอร์ส่ง JSON ผ่าน Serial/MQTT ได้
  - **ตัวเลือกเสริม (Extension):** เพิ่ม Unit Test สั้น ๆ ตรวจสอบขนาด/ชนิดข้อมูลขาออกของโมดูล
  - **แนวทางช่วยเหลือ (Scaffold):** ครูช่วยรีวิวโครงสร้างข้อมูล (Data Format) ระหว่างคนทำฝั่ง Input กับคนทำฝั่ง AI
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, GitHub, อุปกรณ์ของทีม
- **คำถามสะท้อนคิดปิดคาบ:**
  1. รูปแบบข้อมูล (Data Format) ที่ส่วนรับข้อมูลส่งออกมา ตรงกับที่ส่วนประมวลผลต้องการแล้วหรือยัง?

### คาบที่ 23: Sprint 1 (3/4) — พัฒนาส่วนแกนประมวลผล (Core Logic / Baseline)
- **จุดประสงค์การเรียนรู้:**
  1. พัฒนาส่วนประมวลผลแกนหลักของระบบ (เช่น โมเดล Baseline / ตรรกะควบคุมหลัก / Backend Core) ให้รับค่าจากโมดูล Input ได้
  2. ทดสอบการทำงานของส่วนแกนจากต้นจนจบในระดับพื้นฐานได้
- **แนวคิดหลัก:** มุ่งสร้าง "Walking Skeleton" — โครงกระดูกระบบที่ทำงานได้ตั้งแต่ต้นจนจบแม้ฟีเจอร์ยังไม่ครบ เพื่อยืนยันว่าทุกชิ้นส่วนต่อกันติด
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up | เช็กความคืบหน้าครึ่งทางของ Sprint 1 |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (Sprint 1 Day 3)** | ลงมือพัฒนาส่วนแกนหลัก |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** Sprint 1 Day 3 — ส่วนแกนประมวลผล (Walking Skeleton)
  - **โจทย์/สถานการณ์:** เชื่อมโมดูลรับข้อมูลจากคาบ 22 เข้ากับตรรกะ/โมเดลตั้งต้น ให้ได้ผลลัพธ์แรกออกมา
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** โค้ดส่วนแกนหลักที่รับ Input จริงแล้วคืนผลลัพธ์ (Prediction/Decision) ออกมาทาง Console/Log ได้ + Commit บน GitHub
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เขียนโค้ดส่วนแกน (เช่น เทรน Baseline Model รอบแรก หรือ เขียน Rule/Backend Core)
    2. เชื่อมต่อกับโมดูล Input คาบ 22
    3. รันทดสอบตั้งแต่รับ Input จนได้ผลลัพธ์ Output บนหน้าจอ Console
    4. Commit ขึ้น GitHub
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ส่วนแกนทำงานประมวลผลได้จริง (5 คะแนน)
    - เชื่อมต่อกับโมดูล Input คาบ 22 สำเร็จ (3 คะแนน)
    - อัปเดต GitHub และบอร์ดงาน (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ส่งภาพตัวอย่างเข้าฟังก์ชันหลัก → โมเดล Baseline ทำนายคลาสออกมาได้; หรือ เซนเซอร์ส่งค่า → Backend ตัดสินใจสั่งสถานะได้
  - **ตัวเลือกเสริม (Extension):** เก็บค่า Benchmark ตั้งต้น (ความแม่นยำ/ความเร็ว) ของส่วนแกนนี้ไว้เทียบใน Sprint 2
  - **แนวทางช่วยเหลือ (Scaffold):** เน้นให้ใช้โมเดลหรือกฎอย่างง่ายที่สุดก่อน (KISS: Keep It Simple) เพื่อให้แกนวิ่งได้ในคาบนี้
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, GitHub, อุปกรณ์ของทีม
- **คำถามสะท้อนคิดปิดคาบ:**
  1. พรุ่งนี้เป็นวันสุดท้ายของ Sprint 1 เหลืองานไหนอีกบ้างที่จะทำให้ส่วนแกนพร้อมเดโมในคาบ 25?

  2. เตรียมการสาธิตส่วนแกนของระบบ (Sprint 1 Demo) สำหรับการทบทวนในคาบถัดไปได้
- **แนวคิดหลัก:** การรวมโค้ด (Integration) มักเจอปัญหาที่ไม่พบตอนต่างคนต่างทำ การเผื่อ 1 คาบเพื่อรวมและทดสอบก่อน Sprint Review ช่วยให้งานไม่พังหน้าเวที

  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up | ลิสต์เหตุการณ์ที่อาจทำให้ระบบพังตอนผู้ใช้จริงลองเล่น |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (Sprint 3 Day 3)** | เพิ่ม Error Handling, Fail-Safe และปรับจูนความเสถียร |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** Sprint 3 Day 3 — ระบบรวมฉบับทนทาน (Hardened Prototype)
  - **โจทย์/สถานการณ์:** ป้องกันไม่ให้ต้นแบบรวมระบบพังง่าย ๆ เมื่อเจออินพุตผิดปกติหรือการกดใช้งานซ้ำ
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ระบบที่เพิ่ม Error Handling / Fail-Safe แล้ว อย่างน้อย 3 จุด (เช่น ดักไฟล์ผิด, ดักค่าว่าง, แจ้งเตือนเมื่อมั่นใจต่ำ, หรือ Auto-Reconnect) + Commit บน GitHub
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. ทดลองแกล้งระบบด้วยอินพุตแปลก ๆ (เช่น ภาพมืด, ข้อความว่าง, ตัดเน็ต)
    2. ใส่ `try...except` และข้อความแจ้งเตือนผู้ใช้ที่สุภาพอ่านง่าย
    3. ใส่เกณฑ์ Confidence Threshold (ถ้า AI ไม่มั่นใจ ให้แจ้ง `"กรุณาลองใหม่"`)
    4. Commit ขึ้น GitHub
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - มี Error Handling / Fail-Safe ทำงานได้จริง ≥ 3 จุด (5 คะแนน)
    - ระบบไม่แครชเมื่อเจออินพุตผิดปกติพื้นฐาน (3 คะแนน)
    - อัปเดต GitHub และบอร์ดงาน (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** อัปโหลดไฟล์ `.txt` แทนรูปภาพ → หน้าเว็บขึ้นกล่องสีเหลือง `"กรุณาอัปโหลดไฟล์ภาพ (.jpg, .png) เท่านั้น"` โดยแอปไม่พัง
  - **ตัวเลือกเสริม (Extension):** บันทึก Error Log ลงไฟล์ `.log` เพื่อใช้วิเคราะห์ย้อนหลัง
  - **แนวทางช่วยเหลือ (Scaffold):** แจกเช็กลิสต์ 5 วิธีแกล้งระบบให้พัง เพื่อให้นักเรียนลองเทสต์แก้ล่วงหน้า
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, GitHub, อุปกรณ์ของทีม
- **คำถามสะท้อนคิดปิดคาบ:**
  1. พรุ่งนี้ต้องเตรียมระบบให้พร้อมรับการทดสอบกับผู้ใช้จริงในคาบ 35 เหลืออะไรที่ต้องเก็บรายละเอียดอีกบ้าง?

### คาบที่ 34: Sprint 3 (4/4) — เตรียมพร้อมทดสอบผู้ใช้จริง (UAT Preparation)
- **จุดประสงค์การเรียนรู้:**
  1. ปิดงาน Sprint 3 ให้ต้นแบบรวมระบบพร้อมใช้งานจริง 100% บนสภาพแวดล้อมทดสอบได้
  2. ออกแบบบททดสอบ (Test Script) และแบบสอบถามเก็บผลจากผู้ใช้จริงสำหรับคาบ 35 ได้
- **แนวคิดหลัก:** ก่อนให้ผู้ใช้จริงทดสอบ (User Acceptance Testing: UAT) ทีมต้องเตรียมคู่มือสั้น ภารกิจให้ผู้ใช้ลองทำ และแบบบันทึกผลที่เป็นระบบ
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up | ตรวจความพร้อมโค้งสุดท้ายของ Sprint 3 |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (Sprint 3 Day 4)** | ทดสอบ Smoke Test ทั้งระบบ + ทำแบบบันทึก UAT |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ต้นแบบพร้อมทดสอบผู้ใช้ + ชุดเครื่องมือ UAT
  - **โจทย์/สถานการณ์:** เตรียมระบบให้เสถียรที่สุดและสร้างแบบฟอร์มบันทึกผลทดสอบผู้ใช้สำหรับคาบ 35
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** (1) ต้นแบบรวมระบบฉบับ Freeze สำหรับทดสอบ (Tag `v0.3-sprint3` บน GitHub), (2) ใบภารกิจให้ผู้ใช้ทำ 2–3 ข้อ + แบบบันทึกผล UAT (วัดความสำเร็จ, เวลาที่ใช้, ความพึงพอใจ, ข้อเสนอแนะ)
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. ทดสอบเปิดระบบตั้งแต่ต้นจนจบเหมือนวันจริง 2 รอบ
    2. เขียนภารกิจให้ผู้ทดสอบลองทำเอง 2–3 ข้อ (โดยทีมห้ามบอกบท!)
    3. สร้าง Google Form หรือใบจดบันทึกผล UAT
    4. อัปเดตบอร์ดงานและติด Tag บน GitHub
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ต้นแบบรวมระบบพร้อมใช้งานจริงอย่างเสถียร (5 คะแนน)
    - ใบภารกิจและแบบบันทึก UAT ชัดเจนวัดผลได้ (3 คะแนน)
    - GitHub และบอร์ดงานครบถ้วน (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ระบบรันนิ่ง มีใบภารกิจ 3 ข้อ (เช่น "1. ลองสแกนวัตถุ A, 2. ดูคำแนะนำ, 3. ลองกดดูประวัติ") พร้อมฟอร์มเก็บคะแนน 1–5
  - **ตัวเลือกเสริม (Extension):** เตรียมกล้อง/โปรแกรมอัดหน้าจอไว้บันทึกพฤติกรรมผู้ทดสอบ (ขออนุญาตก่อน)
  - **แนวทางช่วยเหลือ (Scaffold):** แจกเทมเพลตแบบบันทึกผล UAT 4 หัวข้อ
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, GitHub, Google Forms, อุปกรณ์ของทีม
- **คำถามสะท้อนคิดปิดคาบ:**
  1. กฎเหล็กตอนให้ผู้ใช้ลองเล่นพรุ่งนี้คืออะไร? (อย่าเถียงผู้ใช้และอย่าบอกบท!)

### คาบที่ 35: ทดสอบ Capstone กับผู้ใช้จริง (User Testing)
- **จุดประสงค์การเรียนรู้:**
  1. ดำเนินการทดสอบต้นแบบ Capstone กับผู้ใช้จริง (เพื่อนต่างกลุ่ม/ครู/กลุ่มเป้าหมาย) อย่างน้อย 3 คนอย่างเป็นระบบได้
  2. บันทึกข้อมูลเชิงปริมาณ (สำเร็จ/ไม่สำเร็จ, เวลา, คะแนน) และเชิงคุณภาพ (จุดที่งง, ข้อเสนอแนะ) ได้
- **แนวคิดหลัก:** User Testing คือกระจกสะท้อนความจริงของนวัตกรรม ผลลัพธ์ที่ได้ไม่ว่าจะดีหรือพังล้วนเป็นข้อมูลล้ำค่าในการปรับปรุงและเขียนรายงาน
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/จัดสถานีทดสอบ | จัดตารางหมุนเวียนทดสอบข้ามกลุ่มหรือเชิญผู้ทดสอบ |
  | **5–42 นาที (74%)** | **โครงงานปลายคาบ (User Testing)** | ให้ผู้ใช้จริง ≥ 3 คนทดลองใช้งานตามภารกิจ + สัมภาษณ์สั้น |
  | 42–50 นาที | สรุปผลเบื้องต้น | ทีมรวมข้อมูลจัดกลุ่มปัญหาตามความรุนแรง (วิกฤต / ปานกลาง / เล็กน้อย) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** รายงานผลทดสอบกับผู้ใช้จริง (Capstone UAT Log)
  - **โจทย์/สถานการณ์:** นำต้นแบบ Sprint 3 ออกสู่สนามทดสอบจริงกับผู้ใช้อย่างน้อย 3 คน
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** บันทึกผลทดสอบผู้ใช้จริง ≥ 3 คน ครบทั้งข้อมูลเชิงปริมาณ (อัตราทำสำเร็จ, คะแนน) และข้อเสนอแนะเชิงคุณภาพ + จัดลำดับปัญหาที่ต้องรีบแก้ในคาบ 36
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. แบ่งคนในทีม: 1 คนต้อนรับอธิบายบริบท, 1 คนสังเกตและจดบันทึกเงียบ ๆ
    2. ให้ผู้ทดสอบทำภารกิจ 2–3 ข้อด้วยตัวเอง (จับเวลาและสังเกตสีหน้า/จุดที่หยุดคิด)
    3. สัมภาษณ์หลังใช้เสร็จ 2 นาทีและให้กรอกคะแนน
    4. สรุปรวมเป็นตารางปัญหาและจัดลำดับความสำคัญสำหรับคาบ 36
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ทดสอบกับผู้ใช้จริงครบ ≥ 3 คนและเก็บข้อมูลครบทั้งปริมาณ-คุณภาพ (5 คะแนน)
    - สังเกตและบันทึกปัญหาอย่างซื่อสัตย์ ไม่เข้าข้างตนเอง (3 คะแนน)
    - จัดลำดับปัญหาที่ต้องแก้ไขได้ชัดเจน (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ทดสอบ 4 คน: 3 คนทำภารกิจสำเร็จใน ~45 วิ, 1 คนกดผิดเพราะปุ่มสีกลืนกับพื้นหลัง, คะแนนเฉลี่ย 4.0/5 → ลิสต์ปัญหา 3 ข้อเตรียมแก้คาบ 36
  - **ตัวเลือกเสริม (Extension):** ทดสอบกับผู้ใช้ที่เป็นกลุ่มเป้าหมายจริงนอกห้องเรียนเพิ่มเติม
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมตารางสรุปผล UAT 3 ช่อง (High Priority / Medium / Nice-to-have)
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ต้นแบบ Capstone, ใบภารกิจและแบบบันทึก UAT จากคาบ 34
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ปัญหาอันดับ 1 ที่ผู้ใช้ส่วนใหญ่เจอตรงกันคืออะไร?

### คาบที่ 36: แก้ไขตามผลทดสอบผู้ใช้และบันทึกผล (1/2)
- **จุดประสงค์การเรียนรู้:**
  1. แก้ไขข้อบกพร่องสำคัญ (High Priority Issues) ที่พบจากการทดสอบผู้ใช้จริงในต้นแบบได้
  2. ทดสอบซ้ำหลังแก้ไขและบันทึกหลักฐานเปรียบเทียบก่อน–หลัง (Before/After) เพื่อเตรียมใส่รายงานได้
- **แนวคิดหลัก:** การแก้ปัญหาที่พบจากผู้ใช้จริงแล้วทดสอบซ้ำยืนยันผล แสดงถึงวงจรการพัฒนาที่สมบูรณ์ (Build–Measure–Learn)
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up | เลือกปัญหาเร่งด่วน 2–3 ข้อจากผล UAT ที่จะแก้ให้เสร็จวันนี้ |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ** | ลงมือแก้ไขต้นแบบ + ทดสอบซ้ำ + บันทึกภาพ Before/After |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ต้นแบบฉบับปรับปรุงหลังทดสอบผู้ใช้ (Post-UAT Fix)
  - **โจทย์/สถานการณ์:** แก้บั๊กและจุดที่ผู้ใช้สับสนจากคาบ 35 ให้เรียบร้อย พร้อมเก็บหลักฐานเปรียบเทียบก่อน–หลัง
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** โค้ด/ต้นแบบที่แก้ไขแล้วบน GitHub + เอกสารภาพเปรียบเทียบ Before vs After ≥ 2 จุด พร้อมผลทดสอบซ้ำ
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. แก้ไขปัญหา High Priority จากคาบ 35 (เช่น ปรับ UI, แก้บั๊กโมเดล/ฮาร์ดแวร์, เพิ่มคำอธิบาย)
    2. ทดสอบซ้ำยืนยันว่าใช้งานได้จริงและไม่พังส่วนอื่น
    3. แคปภาพ/บันทึกตารางเปรียบเทียบ Before vs After
    4. Commit ขึ้น GitHub
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - แก้ไขปัญหาสำคัญจากผลทดสอบผู้ใช้ได้จริง (5 คะแนน)
    - มีหลักฐานเปรียบเทียบ Before/After ชัดเจน (3 คะแนน)
    - โค้ดบน GitHub อัปเดตทำงานได้ปกติ (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** เปลี่ยนปุ่มจากสีเทาเป็นสีเขียวขนาดใหญ่พร้อมไอคอน + เพิ่มเสียง/ข้อความยืนยัน และแคปภาพเทียบชัด
  - **ตัวเลือกเสริม (Extension):** ให้ผู้ทดสอบคนเดิม 1 คนลองกดดูอีกครั้งเพื่อยืนยันว่าปัญหาหายไปแล้ว
  - **แนวทางช่วยเหลือ (Scaffold):** ครูช่วยคัดเลือกปัญหาที่แก้ทันและเห็นผลชัดที่สุดใน 1 คาบ
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, GitHub, ต้นแบบ Capstone
- **คำถามสะท้อนคิดปิดคาบ:**
  1. การแก้ไขวันนี้ช่วยให้ประสบการณ์ผู้ใช้ดีขึ้นอย่างไร และยังเหลือข้อจำกัดอะไรที่ต้องยกไปทำใน ม.6/2?
