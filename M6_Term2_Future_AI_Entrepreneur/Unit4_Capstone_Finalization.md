### คาบที่ 20: ทบทวนข้อเสนอแนะจาก ม.6/1 และวางแผน Sprint ปิดงาน
- **จุดประสงค์การเรียนรู้:**
  1. สังเคราะห์ข้อเสนอแนะทั้งหมดจาก ม.6/1 (Peer Review/รายงานข้อจำกัด) และ ม.6/2 (Market Validation/Pitch) เป็นรายการปรับปรุงที่ชัดเจนได้
  2. วางแผนการพัฒนา **Sprint 4 (คาบ 21–24)** และ **Sprint 5 (คาบ 26–28)** บนบอร์ดงานของทีมได้
- **แนวคิดหลัก:** การปิดงาน Capstone ให้สมบูรณ์ต้องเชื่อมโลกธุรกิจกลับมาปรับแก้ผลิตภัณฑ์จริง โดยแบ่งเป็น 2 สปรินต์สุดท้าย: Sprint 4 เน้นความแม่นยำ/ประสิทธิภาพ และ Sprint 5 เน้นความเสถียร/ปลอดภัย/เอกสาร
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ชี้แจง Roadmap คาบ 20–33 จนถึง Technical Review คาบ 33 |
  | 5–12 นาที | บรรยาย/สาธิต | แนะนำวิธีจัดลำดับ Backlog ปิดงาน (Critical Fixes vs Nice-to-have) |
  | **12–50 นาที (76%)** | **โครงงานปลายคาบ** | ลงมือวางแผนปิดงาน Sprint 4–5 |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** แผนปิดงาน Capstone (Sprint 4–5 Finalization Plan)
  - **โจทย์/สถานการณ์:** ทีมรื้อต้นแบบ `v1.0-term1` จาก ม.6/1 ขึ้นมาตรวจสอบและวางแผนอัปเกรดเป็นฉบับสมบูรณ์
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** เอกสารแผนปิดงาน 1 หน้า + บอร์ด Kanban อัปเดตงานย่อยของ Sprint 4 (เพิ่มความถูกต้อง/ประสิทธิภาพ) และ Sprint 5 (เสถียรภาพ/ความปลอดภัย/ทดสอบผู้ใช้รอบ 2)
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. รวบรวมข้อจำกัดจากรายงาน ม.6/1 และฟีดแบ็กจาก Pitch คาบ 19
    2. กำหนดเป้าหมาย Sprint 4 (เช่น เพิ่มข้อมูลจุดอ่อน, ลดความหน่วง, ปรับปรุงฮาร์ดแวร์)
    3. กำหนดเป้าหมาย Sprint 5 (เช่น Error Handling, PDPA/Security, UAT รอบ 2)
    4. อัปเดตการ์ดงานบน GitHub/Trello พร้อมผู้รับผิดชอบ
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - แผนปิดงานตอบโจทย์ข้อจำกัดเดิมและฟีดแบ็กจริง (4 คะแนน)
    - แบ่งงาน Sprint 4 และ Sprint 5 ชัดเจนสมจริง (4 คะแนน)
    - บอร์ดงานพร้อมเริ่มลงมือในคาบ 21 ทันที (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** แผนระบุชัด: "Sprint 4: เทรนโมเดลใหม่เพิ่มข้อมูล 2 คลาสที่สับสน + ลดเวลาโหลดเว็บจาก 12 วิ เหลือ < 3 วิ; Sprint 5: ใส่ Auto-Reconnect + Consent Banner + ทดสอบผู้ใช้ 5 คน"
  - **ตัวเลือกเสริม (Extension):** ทดลองโคลนและรันโค้ด `v1.0-term1` ขึ้นมาเช็กสภาพแวดล้อมก่อนเริ่มแก้
  - **แนวทางช่วยเหลือ (Scaffold):** แจกเทมเพลตแผนปิดงาน Sprint 4–5
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, GitHub, บอร์ดงาน, รายงานจาก ม.6/1
- **คำถามสะท้อนคิดปิดคาบ:**
  1. มีสภาพแวดล้อมหรือไลบรารีไหนจาก ม.6/1 ที่ต้องอัปเดตหรือติดตั้งใหม่ก่อนเริ่ม Sprint 4 พรุ่งนี้?

### คาบที่ 21: Sprint 4 (1/4) — เพิ่มความถูกต้องของ AI และข้อมูล
- **จุดประสงค์การเรียนรู้:**
  1. ปรับปรุงชุดข้อมูลหรือฝึกโมเดล AI รอบใหม่เพื่อแก้จุดอ่อนจาก ม.6/1 (เช่น คลาสที่ทายผิดบ่อย หรือ Data Drift) ได้
  2. วัดผลเปรียบเทียบความแม่นยำกับรุ่น ม.6/1 บน Test Set มาตรฐานได้
- **แนวคิดหลัก:** Sprint 4 มุ่งเน้น "คุณภาพของสมองกลและประสิทธิภาพหลัก" ของระบบให้ดีกว่าเวอร์ชันต้นแบบใน ม.6/1 อย่างวัดผลได้
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up | ยืนยัน Task แรกของ Sprint 4 |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (Sprint 4 Day 1)** | ลงมืออัปเกรดข้อมูล/โมเดล AI |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** Sprint 4 Day 1 — อัปเกรดโมเดลและข้อมูล (Model v2)
  - **โจทย์/สถานการณ์:** แก้ไขจุดอ่อนความแม่นยำของโมเดล AI/ตรรกะตามแผนคาบ 20
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ไฟล์โมเดล/ตรรกะรุ่นใหม่ + บันทึกตัวเลขเปรียบเทียบความแม่นยำ (ม.6/1 vs Sprint 4) + Commit บน GitHub
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เพิ่มข้อมูลในจุดที่เคยทายผิด หรือปรับปรุง Feature Engineering / Fine-tuning
    2. ฝึกและทดสอบบน Test Set เดิม (หรือ Test Set ที่ขยายให้ครอบคลุมขึ้น)
    3. บันทึกไฟล์โมเดลใหม่และ Commit ขึ้น GitHub
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ลงมือปรับปรุงข้อมูล/โมเดลตรงตามแผน (4 คะแนน)
    - มีตัวเลขวัดผลเปรียบเทียบกับรุ่น ม.6/1 ชัดเจน (4 คะแนน)
    - อัปเดต GitHub และบอร์ดงาน (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** Accuracy เพิ่มจาก 86% → 93% และลด False Positive ในคลาสสำคัญลงครึ่งหนึ่ง
  - **ตัวเลือกเสริม (Extension):** ทดลองลดขนาดโมเดล (Quantization/Pruning เบื้องต้น) เพื่อให้รันเร็วขึ้น
  - **แนวทางช่วยเหลือ (Scaffold):** ครูช่วยตรวจดู Confusion Matrix รอบใหม่
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, Colab GPU, GitHub
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ความแม่นยำของโมเดลวันนี้ดีขึ้นกี่เปอร์เซ็นต์ และส่งผลต่อความเร็วในการประมวลผลหรือไม่?

### คาบที่ 22: Sprint 4 (2/4) — ปรับปรุงประสิทธิภาพฮาร์ดแวร์/ฟีเจอร์หลัก
- **จุดประสงค์การเรียนรู้:**
  1. ปรับปรุงส่วนฮาร์ดแวร์ กลไก หรือฟีเจอร์หลักทางธุรกิจที่ยังขาดใน ม.6/1 ให้สมบูรณ์ขึ้นได้
  2. ทดสอบการทำงานของส่วนที่ปรับปรุงใหม่ร่วมกับระบบหลักได้
- **แนวคิดหลัก:** นอกจากความแม่นยำของ AI แล้ว ฟีเจอร์หลักที่ผู้ใช้เรียกร้อง (เช่น การเก็บสถิติ, กลไกฮาร์ดแวร์ที่แข็งแรงขึ้น) จะทำให้ต้นแบบดูเป็นผลิตภัณฑ์จริง
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up | เช็กความคืบหน้าและ Task วันนี้ |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (Sprint 4 Day 2)** | ปรับปรุงฮาร์ดแวร์/ฟีเจอร์หลัก |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** Sprint 4 Day 2 — อัปเกรดฮาร์ดแวร์และฟีเจอร์หลัก
  - **โจทย์/สถานการณ์:** พัฒนาส่วนกายภาพหรือฟีเจอร์หลักที่ได้รับฟีดแบ็กจากผู้ใช้/กรรมการให้สมบูรณ์
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ฮาร์ดแวร์ที่ปรับปรุงให้แข็งแรง/แม่นยำขึ้น หรือ ฟีเจอร์หลักที่เพิ่มเข้ามาและทดสอบรันผ่านจริง + Commit บน GitHub
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. สาย Hardware: เก็บสายไฟ เปลี่ยนจุดยึดให้แข็งแรง หรือปรับจูนเซนเซอร์/มอเตอร์
    2. สาย Software: พัฒนาฟีเจอร์หลักเพิ่มเติม (เช่น ระบบสรุปสถิติ/ส่งออกรายงาน/คำแนะนำเชิงลึก)
    3. ทดสอบทำงานร่วมกับโมเดลใหม่จากคาบ 21 และ Commit ขึ้น GitHub
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ฮาร์ดแวร์หรือฟีเจอร์หลักได้รับการปรับปรุงจริง (5 คะแนน)
    - ทดสอบทำงานร่วมกับระบบได้ไม่ Error (3 คะแนน)
    - อัปเดต GitHub และบอร์ดงาน (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** กล่องฮาร์ดแวร์ติดตั้งช่องมองกล้อง/เซนเซอร์ใหม่แข็งแรง หรือ เว็บแอปเพิ่มระบบคำนวณสถิติย้อนหลัง 7 วันได้จริง
  - **ตัวเลือกเสริม (Extension):** ปรับโครงสร้างโค้ดให้เป็นโมดูลแยกไฟล์อ่านง่าย (Clean Architecture)
  - **แนวทางช่วยเหลือ (Scaffold):** ครูช่วยดูการรวมฟีเจอร์ใหม่ไม่ให้กระทบโค้ดเดิมที่ทำงานดีอยู่แล้ว
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, GitHub, อุปกรณ์ของทีม
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ฟีเจอร์หรือฮาร์ดแวร์ที่อัปเกรดวันนี้ ช่วยให้เข้าใกล้ผลิตภัณฑ์จริงมากขึ้นตรงไหนบ้าง?

### คาบที่ 23: Sprint 4 (3/4) — ปรับปรุงความเร็ว (Performance) และ UX/UI
- **จุดประสงค์การเรียนรู้:**
  1. ลดความหน่วง (Latency) ของระบบ (เช่น Cache โมเดล, ลดขนาดภาพก่อนส่ง, ปรับความถี่ลูป) ให้ตอบสนองผู้ใช้ได้รวดเร็วขึ้นได้
  2. ปรับปรุงหน้าจอ UX/UI ให้สวยงาม ทันสมัย และสื่อสารกับผู้ใช้ได้ชัดเจนขึ้นได้
- **แนวคิดหลัก:** ประสบการณ์ผู้ใช้ (UX) วัดกันที่ความเร็วและความเข้าใจง่าย การ Cache โมเดลและลดขนาดภาพช่วยลดเวลารอจาก 10 วินาทีเหลือต่ำกว่า 1 วินาทีได้
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up | ตรวจจุดคอขวดความเร็วและจุดขัดตาบน UI |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (Sprint 4 Day 3)** | จูน Performance และขัดเกลา UX/UI |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** Sprint 4 Day 3 — ระบบรุ่นปรับปรุงที่เร็วและใช้งานง่าย
  - **โจทย์/สถานการณ์:** ทำให้ระบบตอบสนองเร็วขึ้นและหน้าตาดูเป็นมืออาชีพพร้อมโชว์ในงาน Final Presentation
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ระบบที่ปรับจูนความเร็ว (พร้อมตัวเลขเวลาตอบสนองก่อน–หลัง) และอัปเกรด UI/UX เรียบร้อย + Commit บน GitHub
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. จับเวลาการทำงานปัจจุบันเพื่อหาจุดที่ช้าที่สุด (Bottleneck)
    2. ปรับปรุงโค้ด (เช่น `@st.cache_resource` ใน Streamlit, โหลดโมเดลครั้งเดียว, Resize ภาพฝั่ง Client)
    3. ปรับสี ฟอนต์ ไอคอน และข้อความบน UI ให้สะอาดตา
    4. วัดเวลาซ้ำหลังปรับปรุงและ Commit ขึ้น GitHub
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ความเร็วตอบสนองดีขึ้นจริง (มีตัวเลขเทียบ) (4 คะแนน)
    - UI/UX สวยงาม ชัดเจน ใช้งานง่าย (4 คะแนน)
    - อัปเดต GitHub และบอร์ดงาน (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ใช้ `@st.cache_resource` โหลดโมเดล → เวลากดทำนายลดจาก 4.5 วิ เหลือ 0.4 วิ และหน้าจอจัดวางเป็น 2 คอลัมน์สวยงาม
  - **ตัวเลือกเสริม (Extension):** ปรับ UI ให้รองรับการเปิดบนหน้าจอมือถือ (Responsive) ได้ดี
  - **แนวทางช่วยเหลือ (Scaffold):** แจกเทคนิค Cache และ Optimization สั้น ๆ สำหรับ Streamlit / Gradio / Node-RED / MicroPython
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, GitHub
- **คำถามสะท้อนคิดปิดคาบ:**
  1. จากจุดที่ช้าที่สุดของระบบ เราสามารถลดเวลาลงไปได้กี่เปอร์เซ็นต์?

### คาบที่ 24: Sprint 4 (4/4) — ทดสอบเปรียบเทียบกับรุ่น ม.6/1 (Benchmark)
- **จุดประสงค์การเรียนรู้:**
  1. รวมงานทั้งหมดใน Sprint 4 และทดสอบ Benchmark เปรียบเทียบประสิทธิภาพระหว่างรุ่น ม.6/1 (`v1.0`) กับรุ่น Sprint 4 (`v2.0`) ได้
  2. สรุปผลการพัฒนา Sprint 4 เพื่อเตรียมนำเสนอใน Sprint 4 Review คาบ 25 ได้
- **แนวคิดหลัก:** ตัวเลข Benchmark (Before vs After) คือหลักฐานสำคัญที่นำไปโชว์ทั้งในรายงานฉบับสมบูรณ์และใน Portfolio ว่าเราพัฒนาผลิตภัณฑ์ให้ดีขึ้นจริง
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | Daily Stand-up | วางแผนรวมโค้ดและเก็บตัวเลข Benchmark |

  - **ตัวเลือกเสริม (Extension):** ซ้อมสถานการณ์จำลอง "ถ้าระบบค้างกลางคัน จะสลับเปิดคลิปสำรองอย่างไรให้ดูเนียน"

### คาบที่ 33: Technical Review ต่อหน้าครู (ตรวจรับทางเทคนิค)
- **จุดประสงค์การเรียนรู้:**
  1. สาธิตการทำงานจริงของระบบฉบับสมบูรณ์และอธิบายโค้ด/ฮาร์ดแวร์/โมเดล AI ต่อหน้าครูผู้สอนได้อย่างลึกซึ้ง
  2. ผ่านเกณฑ์การตรวจรับทางเทคนิค (Technical Sign-off) ทั้งด้านระบบ โค้ด ความปลอดภัย และเอกสาร
- **แนวคิดหลัก:** Technical Review คือการตรวจรับงานวิศวกรรมอย่างเป็นทางการก่อนปล่อยเข้าสู่สัปดาห์ Portfolio และ Final Presentation
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ชี้แจง | แจ้งเกณฑ์ Technical Review (ทีมละ ~7–10 นาที หรือแบ่งสถานีตรวจ) |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (Technical Review)** | ตรวจรับระบบจริง โค้ดใน GitHub, คู่มือ, และตอบคำถามเชิงเทคนิค |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** การตรวจรับทางเทคนิค (Capstone Technical Sign-off)
  - **โจทย์/สถานการณ์:** นำระบบฉบับสมบูรณ์, GitHub Repo, และเอกสารรายงาน/คู่มือ เข้ารับการตรวจประเมินเชิงลึกจากครูผู้สอน
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ผ่านการตรวจรับทางเทคนิค 4 ด้าน (1. ระบบทำงานจริงครบวงจร, 2. โค้ด & GitHub `README` สมบูรณ์, 3. ความปลอดภัย/PDPA/Fail-Safe, 4. รายงาน & คู่มือ) พร้อมใบรับรองผล Technical Review
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. แต่ละทีมสาธิตระบบจริงให้ครูดูทุกฟีเจอร์และ Fail-Safe
    2. ครูสุ่มถามสมาชิกแต่ละคนในทีมเกี่ยวกับส่วนที่รับผิดชอบ (โค้ด, โมเดล, วงจร, เอกสาร)
    3. ครูตรวจ GitHub Repo, `README.md` และรายงานฉบับสมบูรณ์
    4. บันทึกผลการตรวจรับ (ผ่านสมบูรณ์ / ผ่านแบบมีเงื่อนไขต้องแก้จุดเล็กน้อย)
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ระบบทำงานจริงครบถ้วน เสถียร และปลอดภัย (4 คะแนน)
    - สมาชิกทุกคนอธิบายส่วนเทคนิคที่ตนเองทำได้ถูกต้อง (3 คะแนน)
    - เอกสารรายงาน คู่มือ และ GitHub Repo สมบูรณ์ครบถ้วน (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ระบบรันผ่านฉลุย สมาชิกทุกคนตอบคำถามโค้ด/โมเดลส่วนของตัวเองได้ถูกต้อง และเอกสาร/Repo ครบ
  - **ตัวเลือกเสริม (Extension):** เตรียมภาพความสำเร็จจากการตรวจรับวันนี้ไปใส่ใน Portfolio ในคาบ 34
  - **แนวทางช่วยเหลือ (Scaffold):** ทีมที่ติดเงื่อนไขจุดเล็กน้อย ให้เวลาปรับแก้ส่งซ่อมก่อนคาบ 37 (Mock Panel)
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ระบบสมบูรณ์ของทุกทีม, คอมพิวเตอร์, ใบตรวจรับ Technical Review
- **คำถามสะท้อนคิดปิดคาบ:**
  1. เมื่อระบบทางเทคนิคผ่านการตรวจรับแล้ว คุณรู้สึกมั่นใจมากขึ้นแค่ไหนกับการนำไปเขียนเป็นพอร์ตโฟลิโอรายบุคคลในคาบหน้า?
