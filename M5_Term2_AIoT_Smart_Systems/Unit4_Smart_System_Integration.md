# หน่วยที่ 4: Smart System Integration (คาบที่ 27–34)

---

### คาบที่ 27: ออกแบบระบบ (Block Diagram, รายการอุปกรณ์, งบประมาณ, ผังข้อมูล)
- **จุดประสงค์การเรียนรู้:**
  1. เขียนแผนภาพบล็อกระบบ (System Block Diagram) และผังการไหลของข้อมูล (Data Flow Diagram) สำหรับระบบ Smart System ได้
  2. จัดทำรายการอุปกรณ์ (BOM) และประเมินงบประมาณเบื้องต้นได้อย่างสมเหตุสมผล
- **แนวคิดหลัก:** ก่อนประกอบระบบใหญ่ที่รวมทั้งฮาร์ดแวร์ เครือข่าย แดชบอร์ด และ AI ต้องมีเอกสารออกแบบที่ระบุความเชื่อมโยงของทุกส่วนอย่างชัดเจน
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | แนะนำหน่วยที่ 4: การรวมระบบแบบมืออาชีพ (System Integration) |
  | 5–15 นาที | บรรยาย/สาธิต | แสดงตัวอย่าง System Block Diagram, Data Flow, และตาราง BOM + งบประมาณ |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | ร่าง Block Diagram ของระบบ Smart System ประจำกลุ่ม |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** เอกสารออกแบบระบบอัจฉริยะ (Smart System Design Spec)
  - **โจทย์/สถานการณ์:** ทีม (2–4 คน) ต้องออกแบบระบบ Smart System ที่จะสร้างจริงในคาบ 28–34 (เช่น ระบบดูแลแปลงผัก/กระถางต้นไม้, ระบบควบคุมพัดลม/แสงห้องเรียน, ระบบตรวจวัดสิ่งแวดล้อม)
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** เอกสารออกแบบระบบ 1–2 หน้า ประกอบด้วย: (1) Block Diagram ฮาร์ดแวร์และไฟเลี้ยง, (2) Data Flow Diagram (เซนเซอร์ → MQTT → แดชบอร์ด/AI → รีเลย์), (3) ตาราง BOM รายการอุปกรณ์และราคาประมาณการ
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. กำหนดขอบเขตระบบ Smart System ของทีม
    2. วาด Block Diagram ระบุขา GPIO และแหล่งจ่ายไฟแยกส่วน Logic กับ Actuator
    3. วาด Data Flow ระบุชื่อ Topic MQTT และรูปแบบ JSON
    4. ทำตาราง BOM ระบุจำนวนและราคาประมาณการต่อชิ้น แล้วส่งครูอนุมัติท้ายคาบ
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - Block Diagram ครบทุกส่วนและแยกไฟเลี้ยงชัดเจน (4 คะแนน)
    - Data Flow และ Topic MQTT สอดคล้องกัน (3 คะแนน)
    - ตาราง BOM และงบประมาณสมจริงครบถ้วน (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** เอกสารออกแบบ "Smart Desk Lamp & Fan" มีผังต่อ ESP32 + DHT + LDR + รีเลย์, Topic `desk/sensor` และ `desk/cmd`, และตาราง BOM รวมงบ ~650 บาท
  - **ตัวเลือกเสริม (Extension):** ระบุแผนผังการวางตำแหน่งอุปกรณ์ลงในกล่องหุ้ม (Enclosure Layout)
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมเทมเพลตเอกสารออกแบบ 3 ส่วนใน Google Docs/Slides
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, Google Docs/Slides/Draw.io
- **คำถามสะท้อนคิดปิดคาบ:**
  1. การแยก Block Diagram (การต่อสายไฟ) ออกจาก Data Flow (การไหลของข้อมูลซอฟต์แวร์) ช่วยให้ทำงานเป็นทีมง่ายขึ้นอย่างไร?

### คาบที่ 28: ประกอบฮาร์ดแวร์และเดินสายอย่างเป็นระบบ (ขั้นที่ 1)
- **จุดประสงค์การเรียนรู้:**
  1. ประกอบวงจรฮาร์ดแวร์ (ESP32, เซนเซอร์หลายตัว, รีเลย์, ตัวขับ) ตาม Block Diagram ได้อย่างเรียบร้อยและมั่นคง
  2. ทดสอบแยกส่วนฮาร์ดแวร์ (อ่านทุกเซนเซอร์ + สั่งรีเลย์) ก่อนปิดกล่องได้
- **แนวคิดหลัก:** การประกอบฮาร์ดแวร์เพื่อใช้งานจริงต้องยึดอุปกรณ์ให้แน่น เดินสายไฟให้สั้นพอดี แยกสีสายไฟ (+ แดง, - ดำ/น้ำเงิน) และทดสอบก่อนประกอบลงกล่อง
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ตรวจเช็กความพร้อมอุปกรณ์ตาม BOM และย้ำหลักเดินสายเรียบร้อย |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ** | ลงมือทำเอง (ประกอบวงจร + ทดสอบเบื้องต้น) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ชุดฮาร์ดแวร์ Smart System (ระยะที่ 1: เดินสายและทดสอบฐาน)
  - **โจทย์/สถานการณ์:** ประกอบวงจรทั้งหมดตามเอกสารออกแบบคาบ 27 ให้แข็งแรงไม่หลุดง่ายเมื่อเคลื่อนย้าย
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ชุดฮาร์ดแวร์ที่ต่อสายครบทุกตัว (ESP32 + เซนเซอร์ + รีเลย์ + ปั๊ม/พัดลม/LED) ยึดบนแผ่นฐาน/Breadboard แน่นหนา และรันสคริปต์ทดสอบอ่านค่าทุกตัวได้จริง
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. วางจัดตำแหน่งบอร์ดและเซนเซอร์บนแผ่นฐาน
    2. เดินสายไฟด้วยสีมาตรฐาน (+ แดง, GND ดำ) และใช้ Cable Tie/เทปยึดจุดต่อไม่ให้หลุด
    3. ใช้มัลติมิเตอร์เช็กก่อนจ่ายไฟ
    4. รันสคริปต์ Hardware Self-Test อ่านค่าเซนเซอร์ทุกตัวและสั่งรีเลย์ทดสอบ 1 รอบ
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ต่อวงจรตรงตาม Block Diagram ปลอดภัย (4 คะแนน)
    - จัดสายไฟเป็นระเบียบ มั่นคง ไม่หลุดง่าย (3 คะแนน)
    - ทดสอบอ่านทุกเซนเซอร์และขับโหลดได้จริง (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ชุดฮาร์ดแวร์วางเป็นระเบียบ สายไฟแบ่งสีชัดเจน รัน Self-Test อ่านค่า DHT+Soil+Light และคลิกรีเลย์ผ่านหมด
  - **ตัวเลือกเสริม (Extension):** ติดป้ายสติกเกอร์เล็ก ๆ ที่ปลายสายหรือข้างบอร์ดเพื่อบอกหน้าที่แต่ละขา
  - **แนวทางช่วยเหลือ (Scaffold):** ครู/TA เดินตรวจจุดเสี่ยงไฟฟ้าและช่วยไล่เช็กสายที่หลวม
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ESP32, เซนเซอร์, รีเลย์, โหลด DC, สายจัมเปอร์, มัลติมิเตอร์, Cable Tie
- **คำถามสะท้อนคิดปิดคาบ:**
  1. มีสายจุดไหนที่เสี่ยงหลุดหรือโดนน้ำ/ความร้อนเวลาเอาไปใช้งานจริงบ้าง?

### คาบที่ 29: ติดตั้งกล่องหุ้มและความปลอดภัยทางไฟฟ้า (ขั้นที่ 2)
- **จุดประสงค์การเรียนรู้:**
  1. ออกแบบและประกอบกล่องหุ้ม (Enclosure) ที่ป้องกันน้ำ/ฝุ่น/การสัมผัสวงจรไฟฟ้าและระบายอากาศได้ดี
  2. ตรวจสอบความปลอดภัยทางไฟฟ้าขั้นสุดท้ายก่อนเชื่อมต่อซอฟต์แวร์ได้
- **แนวคิดหลัก:** อุปกรณ์ IoT ที่ใช้งานจริงต้องมีกล่องหุ้ม (Enclosure) เพื่อป้องกันไฟฟ้าลัดวงจรจากความชื้นหรือมือสัมผัส และต้องแยกส่วนเซนเซอร์วัดสภาพแวดล้อมให้อยู่ด้านนอกกล่อง
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | แสดงตัวอย่างกล่องหุ้ม (กล่องพลาสติกเจาะช่อง / กล่องกระดาษแข็งเคลือบ) และจุดที่ต้องระวัง (อย่าขังเซนเซอร์ DHT ไว้ในกล่องอับ!) |
  | 5–12 นาที | บรรยาย/สาธิต | แนะนำวิธีเจาะช่องสาย USB, ช่องเซนเซอร์, และยึดบอร์ดในกล่อง |
  | **12–50 นาที (76%)** | **โครงงานปลายคาบ** | ลงมือทำเอง (ประกอบลงกล่องหุ้ม + ตรวจความปลอดภัย) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ชุดฮาร์ดแวร์ Smart System ฉบับใส่กล่องหุ้มพร้อมใช้ (Enclosed Hardware)
  - **โจทย์/สถานการณ์:** นำชุดฮาร์ดแวร์จากคาบ 28 มาติดตั้งลงกล่องหุ้มให้ดูเป็นผลิตภัณฑ์ที่ปลอดภัย ยกเคลื่อนย้ายได้จริงโดยสายไม่หลุด
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ชุดฮาร์ดแวร์ในกล่องหุ้มที่ประกอบเสร็จสมบูรณ์ มีช่องเสียบสาย/ช่องเซนเซอร์พอดี แยกส่วนเปียก-แห้งชัดเจน และผ่านการทดสอบเปิดไฟทำงานได้ปกติ
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เจาะช่องบนกล่องหุ้มสำหรับสาย USB, สายเซนเซอร์ (ยื่นออกด้านนอก), และสายโหลด
    2. ยึดบอร์ด ESP32 และรีเลย์ลงก้นกล่องด้วยนอตรองหรือเทปกาวสองหน้าหนา (ห้ามวางโลหะชิดกัน)
    3. ปิดฝากล่องและติดป้ายชื่อระบบ/คำเตือนความปลอดภัย
    4. ทดสอบจ่ายไฟยืนยันว่าทุกอย่างยังทำงานเหมือนคาบ 28
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - กล่องหุ้มแข็งแรง ปกป้องวงจรและแยกส่วนเปียก-แห้งปลอดภัย (4 คะแนน)
    - ตำแหน่งเซนเซอร์และช่องสายไฟใช้งานสะดวก (3 คะแนน)
    - ทดสอบหลังปิดกล่องแล้วยังทำงานได้ 100% (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** กล่องพลาสติกใสเจาะช่องสายเรียบร้อย เซนเซอร์ DHT ยื่นรับอากาศด้านนอก สายปั๊มน้ำแยกออกอีกฝั่ง และเปิดทำงานได้นิ่ง
  - **ตัวเลือกเสริม (Extension):** ติดตั้งสวิตช์เปิด-ปิดหลักหรือไฟแสดงสถานะ Power LED ไว้ที่หน้ากล่อง
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมกล่องพลาสติก/กล่องกระดาษแข็งสำเร็จรูป คัตเตอร์/สว่านมือ (ครูช่วยเจาะ) และนอตรองบอร์ด
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ชุดฮาร์ดแวร์จากคาบ 28, กล่องหุ้ม (พลาสติก/อะคริลิก/กระดาษแข็ง), เทปกาวสองหน้า, คัตเตอร์/กรรไกร
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ทำไมเซนเซอร์วัดอุณหภูมิ/ความชื้น (DHT) จึงไม่ควรเอาไปซ่อนไว้ในกล่องปิดทึบที่มีบอร์ด ESP32 ร้อน ๆ อยู่ข้างใน?

### คาบที่ 30: เชื่อมซอฟต์แวร์ End-to-End (ขั้นที่ 1: เซนเซอร์ → MQTT → แดชบอร์ด)
- **จุดประสงค์การเรียนรู้:**
  1. เชื่อมต่อกล่องฮาร์ดแวร์เข้ากับ MQTT Broker และแดชบอร์ดให้ส่งข้อมูลครบทุกเซนเซอร์ได้
  2. จัดรูปแบบหน้าแดชบอร์ดให้แสดงผลข้อมูลทั้งหมดของระบบอย่างครบถ้วนและเรียลไทม์ได้
- **แนวคิดหลัก:** ขั้นตอนแรกของการเชื่อมซอฟต์แวร์ (Integration) คือทำให้ข้อมูลจากโลกกายภาพไหลขึ้นสู่แดชบอร์ดได้อย่างถูกต้องและต่อเนื่อง
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ทบทวน Data Flow จากคาบ 27 |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ** | ลงมือทำเอง (เขียนโค้ด MicroPython ส่งขึ้น MQTT + จัดหน้า Dashboard) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ระบบเชื่อมต่อข้อมูลเรียลไทม์ (Live Telemetry Pipeline)
  - **โจทย์/สถานการณ์:** ทำให้กล่องฮาร์ดแวร์จากคาบ 29 ส่งข้อมูลเซนเซอร์ทุกตัวขึ้นแดชบอร์ดพร้อมกันอย่างต่อเนื่อง
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ระบบที่ส่งข้อมูล JSON จากกล่องฮาร์ดแวร์ → MQTT → แดชบอร์ด Node-RED/Blynk แสดงค่าทุกเซนเซอร์เป็นตัวเลข เกจ และกราฟเส้นได้แบบเรียลไทม์
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เขียนโค้ด `main.py` บน ESP32 อ่านเซนเซอร์ทุกตัวและ Publish JSON เข้า Topic หลักของทีม (ใช้ `secrets.py`)
    2. สร้าง/อัปเดต Node-RED Flow รับ JSON และกระจายค่าเข้า Widget ทุกตัว
    3. จัดกลุ่มหน้าจอแดชบอร์ดให้เป็นหมวดหมู่สวยงาม
    4. ทดสอบเปิดรันต่อเนื่อง 5 นาทีเช็กความเสถียรของการอัปเดตข้อมูล
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ข้อมูลจากฮาร์ดแวร์ส่งถึง MQTT ครบทุกตัวแปร (4 คะแนน)
    - แดชบอร์ดแสดงผลถูกต้องเรียลไทม์และอ่านง่าย (4 คะแนน)
    - ใช้ `secrets.py` และโค้ดสะอาด (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** หน้าจอ Node-RED แสดงค่าอุณหภูมิ ความชื้น แสง และสถานะปั๊มอัปเดตทุก 3 วินาทีจากกล่องฮาร์ดแวร์จริง
  - **ตัวเลือกเสริม (Extension):** บันทึกข้อมูลที่เข้ามาลงไฟล์ CSV อัตโนมัติไปพร้อมกันด้วย
  - **แนวทางช่วยเหลือ (Scaffold):** ครูช่วยตรวจโครงสร้าง JSON ฝั่งส่ง (ESP32) ให้ตรงกับฝั่งรับ (Node-RED/Python)
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** กล่องฮาร์ดแวร์จากคาบ 29, คอมพิวเตอร์, MQTT Broker, Node-RED/Blynk
- **คำถามสะท้อนคิดปิดคาบ:**
  1. หากค่าบนแดชบอร์ดไม่อัปเดต เราควรไล่เช็กจุดไหนก่อน (ESP32 ส่งไหม → Broker รับไหม → แดชบอร์ดแปลง JSON ถูกไหม)?

### คาบที่ 31: เชื่อมซอฟต์แวร์ End-to-End (ขั้นที่ 2: โมเดล AI → ควบคุม)
- **จุดประสงค์การเรียนรู้:**
  1. เชื่อมต่อโมเดล AI (ทำนาย/ตรวจความผิดปกติจากหน่วยที่ 3) เข้ากับระบบแดชบอร์ดและคำสั่งควบคุมได้
  2. ปิดวงจรระบบอัจฉริยะครบทุกชั้น (เซนเซอร์ → MQTT → แดชบอร์ด/AI → ควบคุมรีเลย์พร้อม Fail-Safe) ได้
- **แนวคิดหลัก:** เมื่อเชื่อมโมเดล AI เข้ากับการสั่งงานรีเลย์และแดชบอร์ด ระบบจะเปลี่ยนจาก "จอแสดงผล" เป็น "ระบบอัจฉริยะที่คิดและลงมือทำเองได้"
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ตรวจสถานะ Pipeline จากคาบ 30 และวางแผนเสียบโมเดล AI + ควบคุม |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ** | ลงมือทำเอง (เชื่อม AI Worker + ปุ่ม Manual/Auto + Fail-Safe) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ระบบ Smart System เชื่อมต่อครบวงจร (Full-Stack AIoT)
  - **โจทย์/สถานการณ์:** เชื่อมต่อทุกชิ้นส่วนซอฟต์แวร์เข้าด้วยกันให้ทำงานประสานกัน 100% ทั้งโหมดอัตโนมัติ (AI/Rule คุม) และโหมดสั่งมือจากแดชบอร์ด
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ระบบที่เชื่อมต่อครบทั้ง 5 จุด: เซนเซอร์ → MQTT → แดชบอร์ด ↔ โมเดล AI → ควบคุมรีเลย์ (พร้อม Fail-Safe บน ESP32)
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. รันสคริปต์ AI Worker เชื่อมต่อกับ MQTT Broker เพื่อรับข้อมูลจากคาบ 30
    2. ให้ AI Worker ส่งผลทำนายและคำเตือนความผิดปกติขึ้นแดชบอร์ด + ส่งคำสั่งควบคุมไปยัง Topic คำสั่งของ ESP32
    3. เพิ่มปุ่มสลับโหมด `AUTO / MANUAL` บนแดชบอร์ดและปุ่มสั่งเปิด-ปิดด้วยมือ
    4. ทดสอบการทำงานครบวงจรทั้งโหมด Auto และ Manual
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - เชื่อมต่อครบทั้ง 5 ส่วนทำงานประสานกันได้จริง (5 คะแนน)
    - โหมด Auto (AI/Rule) และ Manual ทำงานสลับกันได้ถูกต้อง (3 คะแนน)
    - กลไก Fail-Safe ยังคงทำงานป้องกันอุปกรณ์ได้ (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ค่าเซนเซอร์ขึ้นแดชบอร์ด → AI ทำนายและแจ้งเตือน/สั่งเปิดพัดลม → กดสลับเป็น Manual เพื่อปิดพัดลมจากหน้าเว็บได้
  - **ตัวเลือกเสริม (Extension):** แสดงสถานะยืนยันจริงจาก ESP32 (เช่น "Pump is RUNNING") กลับมาที่แดชบอร์ด
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมตัวอย่าง Logic สลับโหมด Auto/Manual บน Node-RED เพื่อไม่ให้คำสั่งชนกัน
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** กล่องฮาร์ดแวร์, คอมพิวเตอร์, MQTT Broker, Node-RED, ไฟล์โมเดล `.pkl`/`.keras`
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ในโหมด Manual กับ Auto เราควรออกแบบอย่างไรไม่ให้คำสั่งจาก AI ไปเปิดทับตอนที่ผู้ใช้สั่งปิดด้วยมือ?

### คาบที่ 32: ทดสอบระบบด้วย Test Cases (ปกติและผิดปกติ)
- **จุดประสงค์การเรียนรู้:**
  1. ออกแบบชุดทดสอบ (Test Cases) ครอบคลุมทั้งกรณีใช้งานปกติ กรณีขอบเขต และกรณีล้มเหลว (Failure Modes) ได้
  2. ลงมือทดสอบระบบจริงตาม Test Cases และบันทึกผล Pass/Fail เพื่อนำไปแก้ไขได้
- **แนวคิดหลัก:** ระบบที่ทดสอบแค่ "ตอนทำงานปกติ" ยังไม่พร้อมใช้งานจริง ต้องทดสอบตอนเน็ตหลุด ไฟดับ เซนเซอร์หลุด หรือค่าเกินขอบเขตด้วย (QA Testing)
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | อธิบายความสำคัญของการเขียน Test Plan ก่อนส่งมอบงาน |
  | 5–12 นาที | บรรยาย/สาธิต | แสดงตาราง Test Case (ID, สถานการณ์ทดสอบ, ผลที่คาดหวัง, ผลจริง, Pass/Fail) |
  | **12–50 นาที (76%)** | **โครงงานปลายคาบ** | ลงมือทำเอง (เขียน Test Cases ≥ 5 ข้อ + ทดสอบจริง + แก้บั๊ก) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ใบรับรองการทดสอบระบบ (System Test Report)
  - **โจทย์/สถานการณ์:** ทดสอบระบบ Smart System จากคาบ 31 อย่างเข้มข้น อย่างน้อย 5 กรณี (ปกติ 2 กรณี, ผิดปกติ/ล้มเหลว 3 กรณี) เพื่อค้นหาบั๊กที่ซ่อนอยู่
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ตารางผลทดสอบ (Test Report) ≥ 5 Test Cases พร้อมหลักฐานผลจริง (Pass/Fail) และรายการบั๊กที่พบเพื่อเตรียมแก้ในคาบ 33
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เขียน Test Cases 5 ข้อ (เช่น TC1: ทำงานปกติ 5 นาที, TC2: กด Manual Override, TC3: ถอดสายเซนเซอร์ 1 ตัว, TC4: ปิด Wi-Fi ชั่วคราวแล้วเปิดใหม่, TC5: ทดสอบ Fail-Safe ตัดเกินเวลา)
    2. ลงมือทดสอบทีละข้อกับระบบจริงและบันทึกผล
    3. ระบุจุดที่ Fail (เช่น ปิด Wi-Fi แล้วเปิดใหม่ บอร์ดไม่ต่อเอง!) เพื่อนำไปแก้ในคาบ 33
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ออกแบบ Test Cases ครอบคลุมทั้งกรณีปกติและผิดปกติ ≥ 5 ข้อ (4 คะแนน)
    - ทดสอบจริงและบันทึกผลอย่างซื่อสัตย์ครบถ้วน (4 คะแนน)
    - วิเคราะห์สาเหตุของข้อที่ Fail ได้ตรงจุด (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ตาราง 5 ข้อ พบว่า TC4 (Wi-Fi หลุดแล้วต่อใหม่) ได้ผล Fail เพราะบอร์ดค้าง Error → จดไว้แก้ด้วย Auto-Reconnect ในคาบ 33
  - **ตัวเลือกเสริม (Extension):** ทดสอบจับเวลา Stress Test เปิดทิ้งไว้ 15 นาทีต่อเนื่อง
  - **แนวทางช่วยเหลือ (Scaffold):** แจกเทมเพลตตาราง Test Case 5 แถวพร้อมตัวอย่างกรณีทดสอบความล้มเหลว
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ระบบ Smart System จากคาบ 31, คอมพิวเตอร์, Google Sheets/Docs
- **คำถามสะท้อนคิดปิดคาบ:**
  1. จากการทดสอบวันนี้ เจออาการพังข้อไหนที่ทีมไม่เคยคิดมาก่อนว่ามันจะพังได้?

### คาบที่ 33: เพิ่มความเสถียร — Auto-Reconnect และ Watchdog Timer
- **จุดประสงค์การเรียนรู้:**
  1. เขียนโค้ดจัดการข้อผิดพลาด (`try...except`) และเชื่อมต่อ Wi-Fi/MQTT ใหม่อัตโนมัติ (Auto-Reconnect) ใน MicroPython ได้
  2. ใช้ `machine.WDT` (Watchdog Timer) รีเซ็ตบอร์ดอัตโนมัติเมื่อโปรแกรมค้างได้
- **แนวคิดหลัก:** อุปกรณ์ IoT ทำงาน 24 ชั่วโมงโดยไม่มีคนคอยกดปุ่ม Reset จึงต้องมี `try...except` + Auto-Reconnect เพื่อกู้คืนเน็ตหลุด และ Watchdog Timer คอยรีสตาร์ตบอร์ดหากโค้ดค้าง
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ทบทวนข้อที่ Fail จาก Test Report คาบ 32 (Wi-Fi/MQTT หลุดแล้วบอร์ดค้าง) |
  | 5–15 นาที | บรรยาย/สาธิต | สอน `try...except` ครอบ `client.check_msg()` / `publish()`, ฟังก์ชัน `reconnect()`, และ `WDT(timeout=...)` |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | ทดลอง `try...except` กับการดึงสาย/ปิด Hotspot ชั่วคราว |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ระบบ AIoT พันธุ์อึด (Self-Healing ESP32)
  - **โจทย์/สถานการณ์:** แก้ไขโค้ด `main.py` ของระบบ Smart System ให้สามารถกู้คืนตัวเองเมื่อ Wi-Fi/MQTT หลุด และไม่ค้างตาย (ผ่าน Test Case TC4 จากคาบ 32)
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** โค้ด `main.py` ฉบับอัปเกรดที่มี `try...except` + Auto-Reconnect + Watchdog Timer (ตั้ง Timeout เหมาะสม ≥ 10 วินาที) และผลการทดสอบซ้ำ Test Case ที่เคย Fail จนเปลี่ยนเป็น **PASS**
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. ครอบคำสั่งเครือข่าย (`publish`, `check_msg`) ด้วย `try ... except OSError:`
    2. เขียนฟังก์ชัน `ensure_connected()` เช็ก `wlan.isconnected()` และเชื่อมต่อ MQTT ใหม่เมื่อหลุด
    3. เพิ่ม `wdt = WDT(timeout=15000)` และสั่ง `wdt.feed()` ในทุกรอบลูปปกติ (ระวัง: อย่าตั้ง Timeout สั้นเกินไปขณะต่อ Wi-Fi!)
    4. ทดสอบปิด Wi-Fi/Broker 10 วินาทีแล้วเปิดใหม่ ดูบอร์ดต่อกลับเข้าแดชบอร์ดเองโดยไม่ต้องกดปุ่ม Reset
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ใช้ `try...except` และ Auto-Reconnect กู้คืนการเชื่อมต่อได้จริง (5 คะแนน)
    - ใช้ Watchdog Timer อย่างถูกต้องไม่รีเซ็ตพร่ำเพรื่อ (3 คะแนน)
    - ทดสอบซ้ำ Test Case เดิมผ่านเป็น PASS (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ปิด Hotspot มือถือ 10 วินาที → บอร์ดพิมพ์ `Reconnecting...` → เปิด Hotspot → บอร์ดส่งค่าขึ้นแดชบอร์ดต่ออัตโนมัติ
  - **ตัวเลือกเสริม (Extension):** เก็บข้อมูลลง Buffer List ชั่วคราวระหว่างที่เน็ตหลุด แล้วส่งย้อนหลังเมื่อต่อติด
  - **แนวทางช่วยเหลือ (Scaffold):** เตือนเรื่อง Watchdog Timer: แนะนำให้เปิดใช้ WDT *หลัง* ต่อ Wi-Fi รอบแรกเสร็จ หรือ `wdt.feed()` ในลูปรอ Wi-Fi เพื่อไม่ให้รีบูตวนไม่รู้จบ
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ระบบ Smart System, คอมพิวเตอร์
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ถ้าเราตั้ง Watchdog Timeout ไว้ที่ 5 วินาที แต่ตอนต่อ Wi-Fi ใช้เวลา 8 วินาที จะเกิดอะไรขึ้น?
  2. `try...except` ช่วยป้องกันไม่ให้โปรแกรมบน ESP32 หยุดทำงานกลางคันได้อย่างไร?
