### คาบที่ 7: AIoT — Edge AI เทียบกับ Cloud AI
- **จุดประสงค์การเรียนรู้:**
  1. อธิบายความหมายของ AIoT (AI + IoT) และความแตกต่างระหว่างการรัน AI บนอุปกรณ์ (Edge) กับบนคลาวด์ (Cloud) ได้
  2. วิเคราะห์เลือกใช้ Edge AI หรือ Cloud AI ให้เหมาะสมกับข้อจำกัดด้านเวลา อินเทอร์เน็ต และความเป็นส่วนตัวได้
- **แนวคิดหลัก:** Edge AI ประมวลผลใกล้แหล่งกำเนิดข้อมูล จึงตอบสนองไว (Low Latency) ทำงานออฟไลน์ได้ และเป็นส่วนตัวกว่า แต่ประมวลผลโมเดลใหญ่มากไม่ได้เหมือน Cloud AI
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | เทียบกรณี: รถเบรกฉุกเฉิน (รอส่งภาพขึ้น Cloud ไหวไหม?) vs สรุปยอดขายรายเดือน |
  | 5–15 นาที | บรรยาย/สาธิต | เปรียบเทียบ Edge AI vs Cloud AI ใน 4 มิติ: Latency, Bandwidth, Privacy, Compute Power |
  | 15–25 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | วิเคราะห์ 2 ระบบ (ลำโพงอัจฉริยะ vs กล้องตรวจจับคนล้ม) ร่วมกัน |
  | **25–50 นาที (50%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** เมทริกซ์ตัดสินใจสถาปัตยกรรม Edge vs Cloud AI
  - **โจทย์/สถานการณ์:** ทีมสถาปนิก AIoT ต้องเลือกรูปแบบการประมวลผลให้ลูกค้า 4 โครงการ (เช่น โดรนหลบต้นไม้ในป่า, ระบบพยากรณ์อากาศ 7 วัน, กล้องนับคนในร้านค้า, เครื่องตรวจจับเสียงกรน/หกล้มในบ้าน)
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ตารางเปรียบเทียบข้อดี-ข้อจำกัดและคำแนะนำสถาปัตยกรรม (Edge / Cloud / Hybrid) ครบทั้ง 4 โครงการ พร้อมเหตุผลครบ 4 มิติ
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. อ่านโจทย์ทั้ง 4 โครงการและระบุข้อจำกัดของแต่ละงาน (ต้องไวแค่ไหน? เน็ตมีไหม? ภาพส่วนตัวไหม?)
    2. เลือกว่าควรรัน AI ที่ Edge, Cloud หรือ Hybrid (Edge ตรวจเบื้องต้น + Cloud วิเคราะห์ลึก)
    3. เขียนเหตุผลสนับสนุนและแผนสำรองหากเน็ตหลุดหรือแบตต่ำ
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - วิเคราะห์ครบ 4 โครงการและเลือก Edge/Cloud ได้สมเหตุสมผล (5 คะแนน)
    - ใช้เกณฑ์ Latency, Bandwidth, Privacy, Compute ประกอบการตัดสินใจถูกต้อง (3 คะแนน)
    - นำเสนอชัดเจนเข้าใจง่าย (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** "โดรนหลบต้นไม้ → Edge AI เพราะต้องการ Latency ระดับมิลลิวินาทีและในป่าไม่มี Wi-Fi"
  - **ตัวเลือกเสริม (Extension):** ออกแบบสถาปัตยกรรม Hybrid สำหรับ Smart Farm ที่ Edge ตัดสินใจรดน้ำฉุกเฉิน ส่วน Cloud เก็บสถิติรายเดือน
  - **แนวทางช่วยเหลือ (Scaffold):** แจกตารางเปรียบเทียบ Edge vs Cloud 4 มิติเป็นกรอบอ้างอิง
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, LibreOffice Writer / Markdown [เสริม]/Slides
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ทำไมกล้องวงจรปิดอัจฉริยะสมัยใหม่จึงนิยมประมวลผลภาพในตัวกล้อง (Edge) แล้วส่งเฉพาะข้อความแจ้งเตือนขึ้นคลาวด์?
  2. มีงานแบบไหนที่ยังไงก็ต้องพึ่ง Cloud AI?

### คาบที่ 8: เก็บข้อมูลเซนเซอร์ต่อเนื่องพร้อม Timestamp (ขั้นที่ 1)
- **จุดประสงค์การเรียนรู้:**
  1. ตั้งค่าระบบรับข้อมูลจาก MQTT และประทับเวลา (Timestamp) ลงในไฟล์ CSV หรือฐานข้อมูลด้วย Python/Node-RED ได้
  2. ออกแบบโครงสร้างข้อมูลอนุกรมเวลา (Time-Series) ที่เหมาะกับการนำไปสร้างกราฟและฝึก ML ได้
- **แนวคิดหลัก:** ข้อมูลเซนเซอร์จะมีคุณค่ามากขึ้นเมื่อมี **Timestamp** กำกับ ทำให้รู้แนวโน้มการเปลี่ยนแปลงตามเวลา (Time-Series Data)
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ถาม: "ถ้ามีแต่อุณหภูมิ 30, 32, 28 โดยไม่รู้เวลา จะรู้ไหมว่าร้อนตอนเที่ยงหรือเที่ยงคืน?" |
  | 5–15 นาที | บรรยาย/สาธิต | สาธิตสคริปต์ Python (`paho-mqtt` + `datetime`) ดักฟัง Topic แล้ว Append ลงไฟล์ CSV |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | รันสคริปต์ Python Logger รับข้อความทดสอบจาก MQTT ลงไฟล์ `.csv` |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ระบบบันทึกข้อมูลเซนเซอร์อัตโนมัติ (MQTT Time-Series Logger)
  - **โจทย์/สถานการณ์:** สร้างตัวเก็บข้อมูล (Data Logger) บนคอมพิวเตอร์/Node-RED ที่คอยฟังข้อมูล JSON จาก ESP32-S3 แล้วบันทึกลงไฟล์ `iot_data.csv` พร้อม Timestamp ทุกแถว
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** สคริปต์ Data Logger (`mqtt_logger.py` หรือ Node-RED File Out) + ไฟล์ `iot_data.csv` ที่เริ่มเก็บข้อมูลจริงจาก ESP32-S3 ได้ต่อเนื่อง (≥ 20 แถวแรก)
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เปิดใช้งาน ESP32-S3 ที่ Publish ค่าเซนเซอร์ (เช่น ความชื้นดิน/อุณหภูมิ/แสง) ทุก 2–5 วินาที
    2. เขียนสคริปต์ Python (`paho-mqtt`) Subscribe Topic ของทีม
    3. เมื่อมีข้อความเข้า ให้ดึงเวลาปัจจุบัน `datetime.now().isoformat()`, แปลง JSON, และเขียนต่อท้ายไฟล์ `.csv`
    4. เปิดไฟล์ `.csv` ตรวจสอบว่าคอลัมน์และเวลาบันทึกถูกต้อง
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - สคริปต์รับข้อมูล MQTT และประทับเวลา Timestamp ถูกต้อง (4 คะแนน)
    - บันทึกลงไฟล์ CSV โครงสร้างสะอาดพร้อมใช้กับ `pandas` (4 คะแนน)
    - เชื่อมต่อทำงานกับ ESP32-S3 จริงได้ (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ไฟล์ `iot_data.csv` มีหัวตาราง `timestamp,temp,hum,soil,light` และแถวข้อมูลจริงเรียงตามเวลา
  - **ตัวเลือกเสริม (Extension):** เพิ่มการสร้างไฟล์ใหม่รายวันอัตโนมัติ (เช่น `log_2026-11-18.csv`)
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมโค้ด `mqtt_logger.py` โครงร่างให้ทีมใส่แค่ Broker IP, Topic, และชื่อคีย์ JSON
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ESP32-S3-S3 + เซนเซอร์, คอมพิวเตอร์ (Python `paho-mqtt`), MQTT Broker
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ทำไมการประทับเวลาที่ฝั่งเซิร์ฟเวอร์/คอมพิวเตอร์ถึงมักแม่นยำกว่าการให้ ESP32-S3 นับเวลาเอง (ถ้าไม่ได้ซิงค์ NTP)?
  2. ความถี่ในการเก็บข้อมูล (เช่น ทุก 1 วินาที vs ทุก 1 นาที) มีผลต่อขนาดไฟล์และงาน ML อย่างไร?

### คาบที่ 9: สะสมและตรวจสอบชุดข้อมูลอนุกรมเวลาของทีม (ขั้นที่ 2)
- **จุดประสงค์การเรียนรู้:**
  1. เก็บข้อมูลเซนเซอร์ต่อเนื่องจากหลายสภาวะจริง (เช่น ดินแห้ง-ชื้น, ห้องสว่าง-มืด, มีคน-ไม่มีคน) ได้
  2. ตรวจสอบคุณภาพและความครบถ้วนของชุดข้อมูล Time-Series ด้วย `pandas` ได้
- **แนวคิดหลัก:** ข้อมูลสำหรับฝึก AIoT ต้องครอบคลุมการเปลี่ยนแปลงของสภาวะจริง (Variation) ไม่ใช่ค่าคงที่เดิม ๆ ตลอดเวลา
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ตรวจเช็กความพร้อมระบบ Data Logger จากคาบ 8 |
  | 5–10 นาที | แนะนำการทดลอง | วางแผนจำลองการเปลี่ยนสภาวะแวดล้อมขณะเก็บข้อมูลจริง |
  | **10–50 นาที (80%)** | **โครงงานปลายคาบ** | ลงมือทำเอง (เก็บข้อมูลต่อเนื่อง + ตรวจคุณภาพ CSV) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ชุดข้อมูลเซนเซอร์ Time-Series ฉบับสมบูรณ์ (≥ 100 แถว)
  - **โจทย์/สถานการณ์:** เก็บข้อมูลเซนเซอร์ต่อเนื่องให้ได้ ≥ 100 แถว โดยจำลองเหตุการณ์จริง (เช่น รดน้ำดินให้ชื้นแล้วค่อย ๆ แห้ง, ปิด-เปิดไฟ, เป่าลม/ให้ความร้อน) เพื่อใช้สร้างกราฟและฝึกโมเดลในหน่วยที่ 3
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ไฟล์ `iot_team_dataset.csv` (≥ 100 แถว) + โน้ตบุ๊ก `pandas` ตรวจคุณภาพข้อมูล (จำนวนแถว, ช่วงเวลา, ค่า min/max/missing)
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. รัน ESP32-S3-S3 + Logger เก็บข้อมูลต่อเนื่อง
    2. ค่อย ๆ เปลี่ยนสภาวะหน้าเซนเซอร์ทุก ๆ 30 วินาที (เช่น แห้ง → เปียก, มืด → สว่าง) พร้อมจดบันทึกเวลาที่เปลี่ยนสภาวะ
    3. โหลดไฟล์เข้า Python (`pandas`) ตรวจ `df.info()`, `df.describe()`, `df.isnull().sum()`
    4. บันทึกไฟล์เก็บไว้ใช้งานต่อในหน่วยที่ 3
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - เก็บข้อมูลจริงครบ ≥ 100 แถวต่อเนื่อง (4 คะแนน)
    - ข้อมูลมีการเปลี่ยนแปลงครอบคลุมหลายสภาวะจริง (3 คะแนน)
    - ตรวจสอบคุณภาพด้วย `pandas` เรียบร้อย (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ไฟล์ CSV 120 แถว แสดงค่าความชื้นดินขยับจาก 20% → 85% → 60% พร้อมกราฟตรวจสอบเบื้องต้น
  - **ตัวเลือกเสริม (Extension):** เพิ่มคอลัมน์ `status` หรือ `event` เพื่อติดป้ายกำกับสภาวะจริงขณะเก็บข้อมูล
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมโค้ดตรวจสุขภาพ CSV สั้น ๆ 5 บรรทัดให้รันดูผลทันที
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ESP32-S3-S3 + เซนเซอร์, น้ำ/ดิน/ไฟฉายสำหรับจำลองสภาวะ, คอมพิวเตอร์
- **คำถามสะท้อนคิดปิดคาบ:**
  1. จากข้อมูลที่เก็บมาวันนี้ เห็นค่ากระโดดผิดปกติ (Spike) บ้างไหม และเกิดจากอะไร?
  2. ข้อมูล Time-Series ที่เก็บได้วันนี้พร้อมนำไปสร้างกราฟและกฎอัตโนมัติในคาบหน้าหรือยัง?

### คาบที่ 10: แสดงข้อมูลอนุกรมเวลา (Time-Series Visualization)
- **จุดประสงค์การเรียนรู้:**
  1. แปลงคอลัมน์เวลาเป็น `datetime` และพล็อตกราฟอนุกรมเวลาด้วย Python (`pandas`/`matplotlib`) หรือแดชบอร์ด (Grafana/Node-RED) ได้
  2. อ่านแนวโน้ม (Trend) รอบเวลา (Seasonality) และจุดเปลี่ยนแปลงจากกราฟ Time-Series ได้
- **แนวคิดหลัก:** กราฟอนุกรมเวลาช่วยให้เห็นพฤติกรรมของระบบตามแกนเวลา เช่น ความชื้นลดลงชั่วโมงละกี่เปอร์เซ็นต์ หรืออุณหภูมิพุ่งสูงช่วงเวลาใด
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | แสดงตัวอย่างกราฟ Time-Series ของ Smart Farm ที่เห็นรอบการรดน้ำชัดเจน |
  | 5–15 นาที | บรรยาย/สาธิต | สาธิต `pd.to_datetime()`, `df.set_index('timestamp')` และการพล็อตกราฟหลายเส้น |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | โหลด `iot_team_dataset.csv` และแปลงคอลัมน์เวลาสำเร็จ |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** แดชบอร์ดวิเคราะห์แนวโน้มอนุกรมเวลา (Time-Series Insight Report)
  - **โจทย์/สถานการณ์:** วิเคราะห์ชุดข้อมูลจากคาบ 9 เพื่อหาจุดอ้างอิงสำหรับตั้งกฎอัตโนมัติ (เช่น จุดที่ดินแห้งเกินไป หรือเวลาที่ห้องร้อนที่สุด)
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** กราฟอนุกรมเวลา (≥ 2 ตัวแปรเซนเซอร์เทียบกัน) พร้อมเส้น Threshold เป้าหมายและคำอธิบายข้อค้นพบ 3 ข้อ
  - **ขั้นตอนทำงานแบบทีละขั้น:**

### คาบที่ 11: สร้างกฎอัตโนมัติ (Automation Rules & Hysteresis)
- **จุดประสงค์การเรียนรู้:**

  2. ประยุกต์ใช้หลัก Hysteresis (เช่น เปิดเมื่อ < 35%, ปิดเมื่อ > 50%) เพื่อป้องกันอุปกรณ์กระตุกเปิด-ปิดถี่เกินไปได้

  - **ชื่อโครงงาน:** ระบบรดน้ำ/ระบายอากาศอัตโนมัติไร้การกระตุก (Smart Rule Engine)

    1. กำหนดค่า `LOW_THRESH` (จุดเปิด) และ `HIGH_THRESH` (จุดปิด)
    2. เขียนกฎบน Node-RED (Switch Node / Function Node) หรือสคริปต์ Python ควบคุมผ่าน MQTT
    3. เพิ่มโหมดสลับ Auto / Manual บนแดชบอร์ด (เพื่อความปลอดภัย)
    4. ทดสอบจำลองค่าเซนเซอร์ขึ้น-ลง ผ่านช่วงกลางเพื่อยืนยันว่าไม่มีอาการกระพริบรัว
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**

### คาบที่ 13: รับผลทำนายกลับจากโมเดลและตอบสนอง (ขั้นที่ 2)
- **จุดประสงค์การเรียนรู้:**
  1. ส่งผลลัพธ์การทำนายจาก AI Server กลับไปยัง ESP32-S3 และแดชบอร์ดผ่าน MQTT ได้
  2. ทดสอบวงจร AIoT แบบ Round-trip (อุปกรณ์ → เซิร์ฟเวอร์ AI → อุปกรณ์/แดชบอร์ด) ได้สำเร็จ
- **แนวคิดหลัก:** การปิดลูปสื่อสาร (Round-trip) ทำให้ผลวิเคราะห์จาก AI บนเซิร์ฟเวอร์สามารถย้อนกลับมาแสดงบนแดชบอร์ดและสั่งเปิดไฟ/เซอร์โวที่ตัวอุปกรณ์ได้จริง
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ทบทวน `ai_worker.py` จากคาบ 12 |
  | 5–15 นาที | บรรยาย/สาธิต | สาธิตการเพิ่ม `client.publish(result_topic, ...)` ใน `ai_worker.py` และให้ ESP32-S3 Subscribe รับผล |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | ทดลองส่งคำทำนายจาก `ai_worker.py` กลับมาโชว์บน Node-RED Dashboard |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ระบบ AIoT ปิดลูปครบวงจร (Closed-Loop Cloud AIoT)
  - **โจทย์/สถานการณ์:** ต่อยอดคาบ 12 ให้ `ai_worker.py` ส่งผลทำนายกลับไปสั่งงาน ESP32-S3 (เช่น เปิดไฟ/หมุนเซอร์โว) และอัปเดตสถานะขึ้นแดชบอร์ดพร้อมกัน
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ระบบที่ทำงานครบ 4 ขั้นต่อเนื่อง: อุปกรณ์ส่งข้อมูล/ภาพ → AI Server ทำนาย → ส่งผลกลับผ่าน MQTT → อุปกรณ์ตอบสนอง (LED/Servo) + แดชบอร์ดอัปเดต
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เพิ่มคำสั่ง Publish ผลทำนาย (เป็น JSON เช่น `{"class": "plastic", "conf": 0.94}`) ใน `ai_worker.py`
    2. ตั้งค่า ESP32-S3 ให้ Subscribe Topic ผลลัพธ์ (หรือ Topic คำสั่ง) แล้วสั่ง LED/Servo ทำงาน
    3. เพิ่ม Text/Indicator บนแดชบอร์ดให้โชว์คำทำนายล่าสุดจาก AI
    4. ทดสอบทั้งระบบตั้งแต่ต้นจนจบและวัดเวลา Round-trip Latency
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - AI Server ส่งผลกลับเข้า MQTT สำเร็จ (3 คะแนน)
    - อุปกรณ์ ESP32-S3 ตอบสนองตามผลทำนาย AI ได้จริง (4 คะแนน)
    - แดชบอร์ดแสดงผลทำนายล่าสุดพร้อมกับอุปกรณ์ทำงาน (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** กล้อง/เซนเซอร์ส่งข้อมูล → AI ทายคลาส → ใน ~0.5 วินาที เซอร์โวบน ESP32-S3 หมุนไปยังมุมที่กำหนดและหน้าเว็บขึ้นชื่อคลาส
  - **ตัวเลือกเสริม (Extension):** เพิ่มเกณฑ์ Confidence (เช่น ถ้า `< 0.75` ให้ส่งคำสั่ง `"UNCERTAIN"` ไม่ต้องสั่งเซอร์โว)
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมแผนภาพ Topic 3 เส้น (Data Up / AI Result / Device Command) เพื่อไม่ให้ส่งวนทับ Topic เดิม (Infinite Loop!)
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, ESP32-S3-S3 + LED/Servo + เซนเซอร์/กล้อง, MQTT Broker, Node-RED

### คาบที่ 14: Edge AI — รันโมเดลขนาดเล็กใกล้อุปกรณ์
- **จุดประสงค์การเรียนรู้:**
  1. อธิบายเทคนิคการย่อขนาดโมเดลสำหรับ Edge (เช่น การแปลงเป็น โมเดล PyTorch / TorchScript / ONNX ขนาดเล็ก / Quantization หรือใช้โมเดล Decision Tree ขนาดเล็ก) ได้
  2. รันโมเดลขนาดเล็กบนเครื่อง Local Edge (หรือแปลงกฎ Decision Tree ไปรันบน ESP32-S3 โดยตรง) ได้
- **แนวคิดหลัก:** Edge AI ช่วยให้ระบบตัดสินใจได้ทันทีโดยไม่ต้องพึ่งอินเทอร์เน็ต ด้วยการย่อโมเดล (PyTorch Edge/Quantized) หรือแปลงโมเดลอย่างง่ายไปรันบนอุปกรณ์โดยตรง
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ถาม: "ถ้าปิด Wi-Fi/ถอดสายแลน ระบบคาบ 13 จะพังไหม?" |
  | 5–15 นาที | บรรยาย/สาธิต | สาธิตวิธีแปลงโมเดล PyTorch เป็น `.pt (Quantized/TorchScript)` (หรือแปลง `DecisionTree` เป็นฟังก์ชัน Python รันบน ESP32-S3!) |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | ทดลองเช็กขนาดไฟล์ `.pth` เทียบกับ `.pt (Quantized/TorchScript)` (หรือรันกฎ Tree บน ESP32-S3) |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ระบบ AI ออฟไลน์บน Edge (Offline Edge AI Node)
  - **โจทย์/สถานการณ์:** สร้างระบบทำนายที่ทำงานได้แม้ตัดการเชื่อมต่ออินเทอร์เน็ต/คลาวด์ โดยเลือก 1 แนวทาง: (A) แปลงโมเดลภาพเป็น `.pt (Quantized/TorchScript)` รันแบบ Local Edge หรือ (B) แปลงโมเดล Decision Tree เซนเซอร์ให้รันใน MicroPython บน ESP32-S3 โดยตรง
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** สคริปต์ Edge AI ที่ทำงานได้จริงโดยไม่ต้องต่อเน็ต (ทดสอบปิด Wi-Fi/อินเทอร์เน็ต) + บันทึกขนาดโมเดลก่อน-หลังย่อขนาด
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. *แนวทาง A:* ใช้ `torch.jit.script` / `torch.quantization` แปลงเป็น `model.pt` และเขียนโค้ดโหลดรันทำนายแบบออฟไลน์บนเครื่อง Local Edge
    2. *แนวทาง B:* ใช้ `sklearn.tree.export_text(dt_model)` ดูเงื่อนไข แล้วเขียนเป็นฟังก์ชัน `edge_predict(temp, light, soil)` ลงใน ESP32-S3 โดยตรง
    3. ทดสอบตัดการเชื่อมต่อ Cloud/อินเทอร์เน็ต แล้วรันทดสอบการทำงานจริง
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - แปลง/นำโมเดลมาใช้งานแบบ Edge ได้ถูกต้อง (4 คะแนน)
    - ระบบทำงานตัดสินใจได้จริงแม้ไม่มีอินเทอร์เน็ต (4 คะแนน)
    - เปรียบเทียบขนาดไฟล์หรือทรัพยากรที่ใช้ได้ (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** ไฟล์ `.pt (Quantized/TorchScript)` เล็กลงจาก 10 MB เหลือ 2.5 MB รันทำนายออฟไลน์ได้ หรือ ESP32-S3 รันโมเดล Decision Tree ตัดสินใจเปิดไฟได้แม้ปิด Router
  - **ตัวเลือกเสริม (Extension):** เปิดใช้ `converter.optimizations = [tf.lite.Optimize.DEFAULT]` (Quantization) เพื่อลดขนาดลงอีก 4 เท่า
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมโค้ด PyTorch Edge/Quantized Converter 5 บรรทัด และตัวอย่างการแปลง Decision Tree เป็น MicroPython
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, ESP32-S3, โมเดลจากคาบก่อนหน้า
- **คำถามสะท้อนคิดปิดคาบ:**
  1. การแปลงโมเดลเป็น PyTorch Edge/Quantized / Quantization ช่วยลดขนาดไฟล์และเพิ่มความเร็วได้อย่างไร?
  2. ข้อจำกัดของ Edge AI บนไมโครคอนโทรลเลอร์ขนาดเล็กอย่าง ESP32-S3 คืออะไร?

### คาบที่ 15: เปรียบเทียบความเร็วและประสิทธิภาพ Edge AI vs Cloud AI
- **จุดประสงค์การเรียนรู้:**
  1. ออกแบบการทดลองวัดค่าหน่วงเวลา (Latency) และการใช้ทรัพยากรระหว่าง Edge AI กับ Cloud AI ได้
  2. วิเคราะห์ข้อมูลผลการทดลองเพื่อสรุปเกณฑ์การเลือกใช้สถาปัตยกรรมที่คุ้มค่าที่สุดได้
- **แนวคิดหลัก:** วิศวกรต้องตัดสินใจจากตัวเลขจริง (Data-driven) การจับเวลา Latency เฉลี่ย 10 ครั้งเทียบระหว่าง Edge กับ Cloud จะเห็นความแตกต่างอย่างชัดเจน
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ทบทวนระบบ Cloud AIoT (คาบ 13) และ Edge AI (คาบ 14) |
  | 5–15 นาที | บรรยาย/สาธิต | สอนวิธีจับเวลาด้วย `time.perf_counter()` / `time.ticks_ms()` และการหาค่าเฉลี่ย + Max Latency |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | ทดลองจับเวลา Inference 1 รอบและพิมพ์ออกมา |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ศึกประลองความเร็ว Edge vs Cloud Benchmark
  - **โจทย์/สถานการณ์:** ทดสอบรันทำนายข้อมูล/ภาพชุดเดียวกัน 10 ครั้ง ระหว่างโหมด Edge (Local/PyTorch Edge/Quantized/On-device) กับโหมด Cloud/Server (ผ่านเครือข่าย) เพื่อนำตัวเลขมาตัดสินใจออกแบบระบบจริง
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ตารางและกราฟแท่งเปรียบเทียบผลทดสอบ 10 รอบ (Avg Latency, Max Latency, การทำงานเมื่อเน็ตหลุด, และความแม่นยำ) พร้อมบทสรุปแนะนำการใช้งาน
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เตรียมสคริปต์จับเวลาทดสอบ Edge 10 รอบ เก็บค่ามิลลิวินาที (ms)
    2. เตรียมสคริปต์จับเวลาทดสอบส่งผ่านเครือข่ายไป Cloud/Remote Server 10 รอบ เก็บค่า ms
    3. คำนวณค่าเฉลี่ย (Mean) และค่าสูงสุด (Worst-case Max)
    4. วาดกราฟแท่งเปรียบเทียบและเขียนสรุปข้อดี-ข้อเสียจากตัวเลขจริง
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ออกแบบการวัดเวลาทั้ง 2 แบบได้อย่างยุติธรรม (3 คะแนน)
    - เก็บข้อมูลครบ 10 รอบและคำนวณ Avg/Max Latency ถูกต้อง (4 คะแนน)
    - สรุปวิเคราะห์เชื่อมโยงกับการเลือกใช้ในงานจริงได้ชัดเจน (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** กราฟแสดง `Edge Avg: 18 ms` vs `Cloud Avg: 245 ms (Max: 680 ms)` พร้อมสรุปว่างานคุมมอเตอร์เรียลไทม์ต้องใช้ Edge
  - **ตัวเลือกเสริม (Extension):** ทดลองจำลองเน็ตช้าหรือเปิดโหลดหลายเครื่องพร้อมกันแล้วดูว่า Cloud Latency พุ่งขึ้นแค่ไหน
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมโค้ดจับเวลา 10 รอบด้วย `for i in range(10):` และตารางบันทึกผล
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** คอมพิวเตอร์, ESP32-S3, LibreOffice Calc / CSV บน NAS [เสริม]/Matplotlib
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ทำไมค่า Max Latency (Worst-case) จึงสำคัญพอ ๆ กับค่าเฉลี่ย (Average) ในระบบความปลอดภัย?
  2. หากต้องอัปเดตโมเดลให้ฉลาดขึ้นเรื่อย ๆ ทุกสัปดาห์ แบบ Edge หรือ Cloud จัดการง่ายกว่ากัน?

### คาบที่ 16: สั่งอุปกรณ์ปลายทางกำลังสูง (รีเลย์/ปั๊ม/พัดลม) ด้วยผลจาก AI
- **จุดประสงค์การเรียนรู้:**
  1. อธิบายหลักการทำงานของโมดูลรีเลย์ (Relay Module) ในการแยกวงจรควบคุม (3.3V) ออกจากวงจรกำลัง (ปั๊ม/พัดลม) ได้
  2. ต่อวงจรรีเลย์ขับปั๊มน้ำขนาดเล็กหรือพัดลม และเขียนโค้ดสั่งงานจากผลลัพธ์ของ AI/กฎอัตโนมัติได้
- **แนวคิดหลัก:** ESP32-S3 จ่ายกระแสขับปั๊มหรือพัดลมโดยตรงไม่ได้ จึงใช้ "รีเลย์" (สวิตช์แม่เหล็กไฟฟ้า) เป็นตัวกลางให้สัญญาณ 3.3V ไปเปิด-ปิดวงจรไฟเลี้ยงแยกของปั๊ม/พัดลมอย่างปลอดภัย
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ย้ำความปลอดภัย: ใช้เฉพาะแหล่งจ่าย DC แรงดันต่ำ (5V–12V) ห้ามต่อไฟบ้าน 220V ในห้องเรียน! |
  | 5–15 นาที | บรรยาย/สาธิต | อธิบายขาฝั่งควบคุม (VCC, GND, IN) และขาฝั่งสวิตช์ (COM, NO, NC) + Active-LOW vs Active-HIGH |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | ต่อรีเลย์เข้า ESP32-S3 ทดสอบสั่งคลิก เปิด-ปิด (ยังไม่ต่อโหลด) |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ระบบขับเคลื่อนปั๊ม/พัดลมอัจฉริยะผ่านรีเลย์
  - **โจทย์/สถานการณ์:** ต่อยอดระบบ AIoT ให้สามารถสั่งงานอุปกรณ์จริง (ปั๊มน้ำ 5V/12V หรือพัดลม DC) ผ่านโมดูลรีเลย์เมื่อได้รับผลทำนายจาก AI หรือกฎอัตโนมัติ
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** วงจร ESP32-S3-S3 + รีเลย์ + ปั๊มน้ำ/พัดลม (ไฟเลี้ยง DC แยก) ที่รับคำสั่งจาก AI/MQTT เปิด-ปิดทำงานได้จริงอย่างปลอดภัย
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. ตรวจสอบว่าเป็นรีเลย์ Active-LOW หรือ Active-HIGH (ทดสอบกับ LED บนบอร์ดรีเลย์ก่อน)
    2. ต่อขา `COM` และ `NO` (Normally Open) อนุกรมกับแหล่งจ่าย DC และพัดลม/ปั๊มน้ำ (ให้ครูตรวจวงจรก่อนจ่ายไฟ)
    3. เขียนฟังก์ชัน `set_actuator(on)` โดยแปลงตรรกะ Active-LOW ให้เข้าใจง่าย (`0` = เปิด, `1` = ปิด)
    4. เชื่อมกับคำสั่ง MQTT / AI เพื่อทดสอบเปิด-ปิดพัดลม/ปั๊มน้ำจริง
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ต่อวงจรรีเลย์ (COM/NO) และแยกไฟเลี้ยงโหลดถูกต้องปลอดภัย (4 คะแนน)
    - จัดการตรรกะ Active-LOW/HIGH ได้ถูกต้องไม่สลับทิศ (3 คะแนน)
    - รับคำสั่งจาก AI/MQTT เปิด-ปิดปั๊ม/พัดลมได้จริง (3 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** เมื่อ AI ทำนายว่าร้อน/ดินแห้ง → รีเลย์ดังคลิก ไฟสถานะติด พัดลมหมุนทำงาน; เมื่อปกติ → รีเลย์ตัด พัดลมหยุด
  - **ตัวเลือกเสริม (Extension):** เพิ่มหลอด LED แสดงสถานะและสวิตช์ตัดไฟฉุกเฉินแบบฮาร์ดแวร์
  - **แนวทางช่วยเหลือ (Scaffold):** แจกแผนภาพต่อสาย COM–NO เข้ากับพัดลม/ปั๊ม DC 5V–12V และย้ำให้ต่อเฉพาะ `NO` เพื่อให้ปิดเป็นค่าเริ่มต้นเมื่อไฟดับ
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ESP32-S3, โมดูลรีเลย์, พัดลม DC หรือ ปั๊มน้ำขนาดเล็ก, แหล่งจ่ายไฟแยกสำหรับโหลด, ไขควงเล็ก
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ทำไมเราจึงควรต่อสายเข้าช่อง `NO` (Normally Open) แทน `NC` (Normally Closed) สำหรับปั๊มน้ำหรือพัดลม?
  2. รีเลย์แบบ Active-LOW หมายความว่าอย่างไร และอาจทำให้เกิดปัญหาอะไรตอน ESP32-S3 เพิ่งบูตเครื่อง?

### คาบที่ 17: กลไกความปลอดภัย Fail-Safe สำหรับระบบอัตโนมัติ
- **จุดประสงค์การเรียนรู้:**
  1. ออกแบบกลไก **Fail-Safe** ป้องกันความเสียหายเมื่อ AI ทายผิด เซนเซอร์หลุด หรืออินเทอร์เน็ตขาดได้
  2. เขียนโค้ดจำกัดเวลาทำงานสูงสุด (Max Runtime Timeout) และค่าขอบเขตปลอดภัย (Safety Bounds) บน ESP32-S3 ได้
- **แนวคิดหลัก:** ในโลกจริง AI ไม่ได้ถูก 100% และเน็ตอาจหลุดได้ตลอดเวลา ถ้าสั่งเปิดปั๊มน้ำไว้แล้วเน็ตหลุด น้ำอาจท่วมห้อง! จึงต้องฝัง Fail-Safe ไว้ที่ตัว ESP32-S3 เสมอ
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ทบทวน | ยกสถานการณ์: "AI สั่งเปิดปั๊มน้ำ แล้ว Wi-Fi หลุดพอดี คำสั่งปิดส่งมาไม่ถึง จะเกิดอะไรขึ้น?" |
  | 5–15 นาที | บรรยาย/สาธิต | สอน 3 กลไก Fail-Safe: Max Runtime Timeout, Sensor Sanity Check, Confidence Gate |
  | 15–22 นาที | ฝึกปฏิบัติแบบมีผู้ช่วย | เขียนตัวจับเวลาตัดไฟอัตโนมัติ (Auto-off) หลังเปิดเกิน 5 วินาที |
  | **22–50 นาที (56%)** | **โครงงานปลายคาบ** | ลงมือทำเอง |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ระบบควบคุมปั๊ม/พัดลมพร้อมเกราะ Fail-Safe 3 ชั้น
  - **โจทย์/สถานการณ์:** อัปเกรดระบบจากคาบ 16 ให้ปลอดภัยระดับใช้งานจริงได้ แม้ทดลองดึงปลั๊ก Wi-Fi หรือถอดสายเซนเซอร์ออกขณะทำงาน
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** โค้ด MicroPython บน ESP32-S3 ที่มี Fail-Safe ≥ 2 กลไก (1. ตัดการทำงานอัตโนมัติเมื่อเปิดต่อเนื่องเกิน X วินาที, 2. ปิดอุปกรณ์ทันทีเมื่อไม่ได้รับ Heartbeat/เน็ตหลุด หรือเซนเซอร์อ่านค่าเพี้ยน) พร้อมผลทดสอบจำลองเหตุขัดข้องจริง
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. เพิ่มตัวแปร `actuator_start_time`: ถ้าเปิดเกิน `MAX_ON_SEC` (เช่น 10 วิ) ให้ ESP32-S3 สั่งตัดรีเลย์เองทันทีและเข้าสู่โหมด `COOLDOWN`
    2. เพิ่ม Sensor Sanity Check: ถ้าค่าเซนเซอร์เป็น `None` หรือนอกช่วงกายภาพ (เช่น อุณหภูมิ `-999` หรือ `200`) ให้ปิดรีเลย์และแจ้ง `"SENSOR_ERROR"`
    3. ทดสอบจำลองเหตุการณ์: สั่งเปิดพัดลม/ปั๊มแล้วปิด Wi-Fi/Router ดูว่าบอร์ดตัดการทำงานเองได้ตามเวลาที่กำหนดไหม
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - กลไก Max Runtime Timeout ตัดอุปกรณ์เองได้จริง (4 คะแนน)
    - กลไกตรวจสอบค่าเซนเซอร์เพี้ยนหรือเน็ตหลุดทำงานถูกต้อง (4 คะแนน)
    - ทดสอบจำลองเหตุขัดข้องจริงและบันทึกผลได้ (2 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** สั่งเปิดปั๊มผ่าน MQTT แล้วปิด Wi-Fi → ครบ 10 วินาที ESP32-S3 ตัดรีเลย์ปิดปั๊มเองทันที พร้อมขึ้นข้อความ `FAIL-SAFE TRIGGERED`
  - **ตัวเลือกเสริม (Extension):** เพิ่มปุ่มกดฉุกเฉิน (Hardware E-Stop) บนบอร์ดที่ตัดรีเลย์ทันทีเมื่อกด
  - **แนวทางช่วยเหลือ (Scaffold):** เตรียมโค้ด Pattern จับเวลา `time.ticks_diff(time.ticks_ms(), start_ms)` บน ESP32-S3
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ESP32-S3-S3 + รีเลย์ + พัดลม/ปั๊ม + เซนเซอร์ จากคาบ 16
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ทำไมกลไก Fail-Safe ต้องเขียนฝังไว้บนตัวบอร์ด ESP32-S3-S3 DevKitC-1 N16R8 (Local) ไม่ควรฝากไว้ที่ Cloud/Dashboard?
  2. หากระบบรดน้ำตัดการทำงานเพราะ Max Runtime Timeout เราควรแจ้งเตือนผู้ใช้ทางไหนบ้าง?

### คาบที่ 18: ทดสอบปฏิบัติ AIoT ครบวงจร (Sense → Network → AI → Fail-Safe Act)
- **จุดประสงค์การเรียนรู้:**
  1. บูรณาการระบบ AIoT ครบวงจร (อ่านเซนเซอร์ → ส่งผ่าน MQTT → ประมวลผล AI → แสดงแดชบอร์ด → สั่งรีเลย์พร้อม Fail-Safe) ด้วยตนเองได้
  2. ทดสอบและแก้ปัญหาการเชื่อมต่อระหว่างฮาร์ดแวร์ เครือข่าย และซอฟต์แวร์ AI ได้
- **แนวคิดหลัก:** การทดสอบปฏิบัติครบวงจรช่วยยืนยันว่าองค์ประกอบทั้ง 4 ชั้นของ AIoT ทำงานประสานกันได้จริงก่อนก้าวสู่ Applied ML และการประกอบระบบใหญ่
- **ตารางเวลา:**
  | ช่วงเวลา | กิจกรรม | วิธีสอน |
  |---|---|---|
  | 0–5 นาที | เปิดคาบ/ชี้แจง | แจ้งโจทย์ทดสอบปฏิบัติและเกณฑ์ตรวจ |
  | **5–50 นาที (90%)** | **โครงงานปลายคาบ (สอบปฏิบัติ)** | ลงมือทำเอง (ครูและ TA ตรวจการทำงานครบวงจรหน้าโต๊ะ) |
- **โครงงานปลายคาบ:**
  - **ชื่อโครงงาน:** ภารกิจสร้างระบบ AIoT ครบวงจรใน 45 นาที
  - **โจทย์/สถานการณ์:** สร้างระบบอัจฉริยะขนาดย่อมตามโจทย์ที่กำหนด (เช่น ระบบระบายอากาศอัจฉริยะ หรือ ระบบดูแลความชื้นอัตโนมัติ) ที่อ่านเซนเซอร์ ส่งขึ้น MQTT/Dashboard ผ่านโมเดล AI (หรือกฎอัจฉริยะ) และสั่งรีเลย์/LED พร้อม Fail-Safe
  - **ชิ้นงานที่ต้องส่ง (Deliverable):** ระบบ AIoT ที่ทำงานได้จริงครบ 4 ส่วน: ESP32-S3-S3 + เซนเซอร์, MQTT + Dashboard, โมเดล AI/Rule ตัดสินใจ, และรีเลย์/LED ที่มี Fail-Safe
  - **ขั้นตอนทำงานแบบทีละขั้น:**
    1. ต่อวงจรเซนเซอร์ + รีเลย์/LED บน ESP32-S3
    2. รันโค้ด MicroPython เชื่อม Wi-Fi/MQTT (ใช้ `secrets.py`) พร้อม Fail-Safe Timeout
    3. เปิด MQTT Broker + Node-RED Dashboard + Python AI Worker
    4. สาธิตให้ครูตรวจ: เปลี่ยนค่าหน้าเซนเซอร์ → ดูกราฟบนแดชบอร์ด → AI สั่งเปิดรีเลย์ → ทดสอบ Fail-Safe ตัดเอง
  - **เกณฑ์ประเมิน (Rubric ย่อ 10 คะแนน):**
    - ฮาร์ดแวร์อ่านเซนเซอร์และขับรีเลย์/LED ได้ปลอดภัย (3 คะแนน)
    - การสื่อสาร MQTT และแดชบอร์ดทำงานเรียลไทม์ (3 คะแนน)
    - AI/Rule ตัดสินใจสั่งงานและมี Fail-Safe ทำงานได้จริง (4 คะแนน)
  - **ตัวอย่างผลงานที่ถือว่าผ่าน:** เอามือบังแสง/เป่าลมร้อนใส่เซนเซอร์ → ค่าขึ้นแดชบอร์ด → AI สั่งเปิดพัดลม → ปล่อยไว้ครบเวลา Fail-Safe ตัดพัดลมเอง
  - **ตัวเลือกเสริม (Extension):** เพิ่มโหมดสลับ Auto/Manual บนแดชบอร์ดให้สมบูรณ์
  - **แนวทางช่วยเหลือ (Scaffold):** อนุญาตให้ใช้โค้ดเดิมจากคาบ 1–17 ของตนเองเป็นฐานได้ (Open-notes)
- **วัสดุ/เครื่องมือที่ต้องเตรียม:** ชุดอุปกรณ์ ESP32-S3, เซนเซอร์, รีเลย์, พัดลม/LED, คอมพิวเตอร์
- **คำถามสะท้อนคิดปิดคาบ:**
  1. ส่วนไหนของระบบ AIoT ที่เชื่อมต่อยากที่สุดหรือใช้เวลาดีบักนานที่สุดในการสอบวันนี้?
  2. ในหน่วยถัดไป เราจะนำข้อมูลอนุกรมเวลาที่เก็บได้มาสร้างโมเดลทำนายล่วงหน้าและตรวจจับความผิดปกติอย่างไร?
